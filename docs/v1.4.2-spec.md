# OpenJatoBID v1.4.2 知识库、设备授权与管理端升级修复规格

## 1. 文档用途

本规格用于指导 Codex 在本地分支：

```text
codex/opencode-isolation-kb-long-doc
```

上继续开发。

本次只处理试运行和代码审计确认的六个问题，不重新实施已经完成的 OpenCode 隔离、知识库超长文件分段、本地渲染或更新发布链路。

---

# 2. 已确认的问题

## 问题 1：知识库文件夹重命名按钮点击无反应

当前前端按钮已经绑定重命名函数，IPC、Service 和 SQLite 更新链路也已经存在，但前端使用：

```ts
window.prompt('请输入新的文件夹名称', currentName)
```

作为重命名输入入口。Electron Renderer 中该原生交互不稳定，也没有受控状态、错误显示和保存状态，因此用户点击后可能没有任何可见响应。

### 目标

使用应用内受控 Dialog 完成重命名，不再依赖 `window.prompt`。

---

## 问题 2：知识库查看条目页面布局不合理

当前查看页将文件信息和所有操作按钮放在同一个可换行 Flex 容器中。长文件名会挤压右侧按钮，导致按钮排列不规则，页面信息层级不清晰。

### 目标

按照用户提供的布局调整为明确的查看页 Header：

```text
知识库 | 文件名称 | XX 条知识 | 返回知识库 | 知识条目
                                           | Markdown
```

---

## 问题 3：查看条目页面的长文件名不能换行显示

当前 Viewer 文件名使用：

```css
white-space: nowrap;
text-overflow: ellipsis;
```

因此长文件名只能显示单行省略文本。

### 目标

文件名区域占据主要可用宽度，支持中文、英文和连续字符自然换行，不覆盖操作按钮，不产生横向滚动条。

---

## 问题 4：授权申请记录、员工数量和设备绑定数量口径混淆

当前管理端存在三类不同数据：

1. 授权申请记录；
2. 已授权员工；
3. 实际有效设备绑定。

但页面和后端计数口径没有清晰区分：

- “申请记录”的角标只统计待审批申请，而不是申请记录总数；
- “员工与设备”的角标实际统计员工人数；
- 员工卡片的有效设备数按 ACTIVE License 行数统计；
- 同一台电脑多次提交申请后，可能形成多条申请、设备或许可记录；
- 这些重复记录可能被计入设备绑定数量，导致同一台电脑占用多个设备名额。

### 目标

明确区分：

```text
申请记录数量
授权员工数量
有效设备绑定数量
```

同一台电脑重复申请可以保留申请历史，但审批后只能对应一个有效设备绑定，只占用一个设备名额。

---

## 问题 5：客户端更新或重装后，已授权用户无法登录

当前设备指纹包含安装级 `clientId` 和易变化的网卡 MAC 集合；客户端的管理端地址、公钥和本地 License 又保存在 Electron `userData` 中。

更新、重装、配置重建或网络适配器变化后，可能出现：

- `clientId` 变化；
- 设备指纹变化；
- 管理端地址丢失；
- 固定公钥丢失；
- 本地 License 丢失；
- 管理端无法将当前客户端识别为原来已授权的电脑。

### 目标

已授权用户在同一台电脑上更新或重装客户端后：

```text
输入原姓名和手机号
→ 自动连接原管理端
→ 识别为原设备
→ 重新签发本地 License
→ 正常登录
```

不得要求重新提交授权申请，不得重复占用设备名额。

---

## 问题 6：管理端更新后管理员账号可能无法登录

当前管理端账号保存在 `management.sqlite3` 的 `admin_auth` 表中。

已经处于：

```text
OWNER_PASSWORD_ACTIVE
```

状态的管理员，现有代码不会被新安装包的初始凭据覆盖，正常覆盖更新原则上可继续使用原账号和密码。

但仍存在三类风险：

1. 旧版 `LEGACY` 管理员迁移时，现有逻辑会使用新安装包初始凭据覆盖旧密码；
2. 管理端数据库依赖 Electron `userData` 路径，产品名或数据路径变化可能导致新版本读取空数据库；
3. 数据库迁移前没有明确的文件级备份和失败恢复门禁。

### 目标

管理端更新或重装后：

- 已激活管理员账号和密码保持不变；
- 初始密码尚未修改的账号保持原状态；
- 旧版管理员密码迁移后仍可使用；
- 更新不得因数据目录变化创建一个新的空管理员数据库；
- 数据库迁移失败不得重置管理员账号。

# 3. 实施范围总表

## A. 知识库文件夹重命名

- A1：移除 `window.prompt`。
- A2：新增应用内受控重命名 Dialog。
- A3：默认填入当前名称并自动聚焦、全选。
- A4：Enter 提交，Esc 和取消按钮关闭。
- A5：空名称不允许提交。
- A6：名称未变化时关闭弹窗，不调用 IPC。
- A7：保存期间禁用重复提交。
- A8：IPC 失败时保留弹窗和输入内容，并显示错误。
- A9：成功后立即更新当前文件夹名称。
- A10：拖拽、排序和删除功能不得回退。

## B. 知识库查看页布局

- B1：Viewer Header 使用独立 Grid，不再直接复用首页 Flex 布局。
- B2：桌面端固定为“知识库 / 文件名 / 条目数 / 返回 / 模式切换”。
- B3：文件名支持多行。
- B4：中文、英文和连续字符都可换行。
- B5：“返回知识库”独立显示。
- B6：“知识条目”和“Markdown”垂直排列。
- B7：开发者按钮放入独立辅助操作区。
- B8：窄窗口允许 Header 分行，但按钮顺序不变。
- B9：不得产生横向滚动或按钮覆盖。
- B10：条目列表、查看原文和 Markdown 功能不变。

## C. 授权申请、员工和设备数量分离

- C1：申请记录数、待审批数、员工数、有效设备数使用独立统计字段。
- C2：“申请记录”角标显示申请记录总数，页面内另显示待审批数量。
- C3：“员工与设备”区域同时显示员工数和有效设备绑定数。
- C4：员工卡片显示该员工唯一有效设备绑定数。
- C5：授权申请记录本身不占设备名额。
- C6：员工记录本身不占设备名额。
- C7：只有唯一有效设备绑定占设备名额。
- C8：同一台电脑重复申请不新增设备数。
- C9：同一台电脑最多保留一个 ACTIVE License。
- C10：设备上限仍为每名员工最多 3 台不同电脑。

## D. 稳定设备码和重装登录恢复

- D1：新增稳定 `deviceCode`。
- D2：Windows 使用 MachineGuid；macOS 使用 IOPlatformUUID；Linux 使用 machine-id。
- D3：`deviceCode` 不包含 `clientId`。
- D4：`deviceCode` 不包含 MAC 地址。
- D5：`deviceCode` 不包含客户端版本、安装路径、用户名或员工信息。
- D6：同一电脑更新、重装、切换网络后 `deviceCode` 不变。
- D7：`clientId` 只用于安装实例、Analytics 和诊断。
- D8：保留旧 `deviceFingerprint` 兼容旧客户端和旧 License。
- D9：管理端以 `employee_id + deviceCode` 作为新设备唯一键。
- D10：同一 Device Code 的重复申请更新原设备绑定。
- D11：新旧客户端可在迁移期同时登录。
- D12：新版客户端首次登录时可为唯一匹配的旧设备回填 Device Code。
- D13：无法唯一判断的历史记录不得静默绑定错误设备。
- D14：更新或重装后原授权用户直接登录，不重新申请。
- D15：重装后重新签发本地 License，不增加设备数量。

## E. 客户端连接信息恢复

- E1：新增固定 Jato Bootstrap Store。
- E2：Bootstrap Store 不依赖 Electron 产品名和版本对应的 `userData` 目录。
- E3：保存管理端服务器地址。
- E4：保存已固定的管理端公钥。
- E5：不得保存模型 API Key、投标文件、管理端密码或 License 私钥。
- E6：`user_config.json` 缺失连接信息时，从 Bootstrap 恢复。
- E7：成功连接管理端后同步更新 Bootstrap。
- E8：固定公钥发生变化时继续拒绝静默信任。
- E9：Bootstrap 缺失时提供管理端地址恢复入口。
- E10：恢复地址后执行正常登录，不自动进入授权申请流程。

## F. 撤销授权、在线踢下线和延迟清理

- F1：管理端撤销后，设备行立即从普通设备列表消失。
- F2：设备额度立即释放。
- F3：管理端创建内部撤销墓碑，不在普通 UI 中显示。
- F4：客户端在线时通过实时通道立即收到撤销事件并退出授权状态。
- F5：客户端离线时，在下一次启动、登录、网络恢复、心跳或验证时立即失效。
- F6：半小时周期验证继续作为实时通知失败时的兜底。
- F7：客户端收到撤销或未授权结果后，在本地 License 元数据中持久化失效状态。
- F8：不要求删除整个 `license.json` 文件。
- F9：服务器已确认失效后，不得继续使用旧离线授权。
- F10：撤销墓碑保留期为当前离线授权窗口 30 天。
- F11：客户端确认收到撤销后，可以提前清理对应墓碑。
- F12：客户端长期未上线时，30 天后自动清理撤销墓碑和关联许可残留数据。
- F13：墓碑清理后，旧 License 再次验证仍返回 `NOT_AUTHORIZED`。
- F14：主动撤销的设备若再次使用，需要重新申请授权。

## G. 管理端管理员账号升级保护

- G1：`OWNER_PASSWORD_ACTIVE` 账号更新后保持用户名、密码 Hash、Salt 和状态不变。
- G2：`INITIAL_PASSWORD_REQUIRED` 账号更新后保持原初始凭据，不使用新安装包凭据覆盖。
- G3：旧 `LEGACY` 管理员迁移时保留旧密码 Hash 和 Salt。
- G4：旧 `LEGACY` 数据迁移后使用确定的管理员用户名，但不得替换旧密码。
- G5：新安装包内置初始凭据只允许用于全新空数据库。
- G6：管理端数据库迁移前必须备份。
- G7：迁移失败时保留原数据库，不创建空数据库掩盖错误。
- G8：管理端数据目录使用固定 Jato 路径，不能依赖可变化的产品名。
- G9：首次启用固定目录时，安全迁移旧 `management.sqlite3`。
- G10：管理端 `name`、`appId`、`productName` 作为受保护发行字段。
- G11：覆盖更新和重装后原管理员账号仍可登录。
- G12：管理员数据库无法迁移时，管理端显示明确错误并停止业务服务，不自动重置账号。

# 6. 授权统计和数据模型

## 6.1 统计口径

管理端返回独立统计：

```ts
interface AuthorizationSummary {
  applicationCount: number;
  pendingApplicationCount: number;
  employeeCount: number;
  activeDeviceBindingCount: number;
}
```

定义：

- `applicationCount`：全部授权申请记录数；
- `pendingApplicationCount`：状态为待审批或设备上限的申请数；
- `employeeCount`：至少有一台有效或过期设备记录的员工数；
- `activeDeviceBindingCount`：唯一有效 Device Code 数量。

## 6.2 页面展示

建议：

```text
申请记录 12
待审批 2

员工 8
有效设备 11
```

不得继续用 `employees.length` 代替设备数量。

## 6.3 有效设备唯一键

新数据：

```text
employee_id + device_code
```

旧数据过渡：

```text
有 device_code：employee_id + device_code
无 device_code：employee_id + client_id
client_id 也为空：employee_id + device_fingerprint
```

同一唯一键只能有一个 ACTIVE License。

# 7. 稳定 Device Code

新增：

```js
const DEVICE_CODE_VERSION = 'jato-device-v1';
```

原始材料：

### Windows

```text
APP_ID + platform + MachineGuid + DEVICE_CODE_VERSION
```

### macOS

```text
APP_ID + platform + IOPlatformUUID + DEVICE_CODE_VERSION
```

### Linux

```text
APP_ID + platform + machine-id + DEVICE_CODE_VERSION
```

最终：

```js
deviceCode = sha256(canonicalSource);
```

不得加入：

```text
analytics_client_id
clientId
MAC
IP
客户端版本
安装目录
用户目录
姓名
手机号
```

协议新增：

```json
{
  "deviceCode": "...",
  "deviceCodeVersion": "jato-device-v1",
  "deviceFingerprint": "旧兼容字段",
  "clientId": "安装实例字段"
}
```

适用于：

```text
POST /api/v1/authorization/applications
POST /api/v1/authorization/login
POST /api/v1/authorization/verify
```

新 License Payload 同时保留新旧设备字段。

新客户端校验：

1. 有 `deviceCode` 时比较 Device Code；
2. 无 `deviceCode` 时比较旧 Fingerprint；
3. 均不匹配则设备不匹配。

# 9. 管理端数据库迁移和重复设备合并

## 9.1 新字段

`devices` 增加：

```sql
device_code TEXT;
device_code_version TEXT;
```

`authorization_applications` 增加：

```sql
device_code TEXT;
device_code_version TEXT;
```

唯一索引：

```sql
CREATE UNIQUE INDEX idx_devices_employee_device_code
ON devices(employee_id, device_code)
WHERE device_code IS NOT NULL AND device_code <> '';
```

## 9.2 旧数据回填

管理端不能从旧 Hash 反推 MachineGuid，因此旧 Device Code 初始为空。

新版客户端第一次登录时：

1. 精确匹配 Device Code；
2. 未找到时匹配旧 Fingerprint；
3. 再尝试同一员工下唯一的相同 Client ID；
4. 只有唯一候选才能回填 Device Code；
5. 多候选时执行明确的重复合并；
6. 无法唯一判断时返回迁移冲突，不得随机绑定。

## 9.3 重复合并

同一员工下，满足以下任一条件的记录可以进入重复候选：

- Device Code 相同；
- 旧 Client ID 相同且非空；
- 新客户端旧 Fingerprint 精确匹配后，发现同 Client ID 重复记录。

Canonical Device 优先级：

1. 有 ACTIVE License；
2. `last_verified_at` 最新；
3. `updated_at` 最新；
4. 稳定 ID 排序。

合并后：

- 最多保留一个 ACTIVE License；
- 有效期取有效记录最大值；
- 最近校验时间取最大值；
- 当前 Client ID、平台和架构更新到 Canonical Device；
- 重新签发 License Envelope；
- 删除多余 Device 和 License；
- 申请历史可以保留，但不参与设备数计算。

# 10. 撤销授权状态机

## 10.1 数据结构

新增内部表：

```sql
authorization_revocations (
  id TEXT PRIMARY KEY,
  license_id TEXT NOT NULL,
  employee_id TEXT NOT NULL,
  device_code TEXT,
  legacy_device_fingerprint TEXT,
  revoked_at TEXT NOT NULL,
  acknowledged_at TEXT,
  purge_after TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```

该表不在普通员工设备列表显示。

## 10.2 撤销事务

管理员确认撤销后，在同一事务中：

1. 创建撤销墓碑；
2. 从有效设备列表移除 Device；
3. 删除或归档 ACTIVE License；
4. 立即释放设备额度；
5. 发布实时撤销事件；
6. 返回成功。

普通 UI 不显示“已撤销”设备行。

## 10.3 在线客户端立即踢下线

仅靠半小时验证不能满足“立即”。

实现一个管理端到客户端的实时撤销通道，优先采用：

```text
SSE 或等价的持续 HTTP 事件流
```

要求：

- 登录成功后客户端订阅当前 License/Device 的撤销事件；
- 管理端撤销后立即发布事件；
- 客户端收到事件后立即切换未授权状态；
- 当前页面退出到登录页；
- 不等待半小时周期校验；
- 实时通道断开时自动重连。

不得在 URL 查询参数中暴露完整 License 或敏感身份信息；使用短期 Watch Token 或等价安全凭据。

## 10.4 离线客户端上线即失效

客户端在以下时机必须验证：

- 应用启动；
- 登录；
- 网络从离线恢复；
- 实时通道重连；
- 半小时周期校验。

命中撤销墓碑返回：

```text
REVOKED
```

墓碑已清理但授权不存在时返回：

```text
NOT_AUTHORIZED
```

两者都必须立即退出授权。

## 10.5 本地 License

收到 `REVOKED` 或 `NOT_AUTHORIZED` 后：

- 不删除整个 `license.json`；
- 更新 `local.serverStatus`；
- 记录服务器确认时间；
- 禁止继续离线授权；
- 重启后仍保持未授权。

示例：

```json
{
  "local": {
    "serverStatus": "REVOKED",
    "revokedAt": "...",
    "lastAttemptAt": "..."
  }
}
```

## 10.6 清理期限

当前离线授权窗口是 30 天，因此撤销墓碑保留：

```text
30 天
```

规则：

- 客户端确认收到撤销后，可以提前清理墓碑；
- 长期未上线时，30 天后自动清理撤销墓碑和许可残留；
- 清理后旧 License 请求仍返回 `NOT_AUTHORIZED`；
- 清理任务不得影响正常设备和过期设备。

# 11. 管理端管理员账号升级保护

## 11.1 固定管理端数据目录

新增管理端固定数据根目录，例如：

```text
%LOCALAPPDATA%\JatoDigital\OpenJatoBID-Management\
```

其中：

```text
management.sqlite3
management.sqlite3-wal
management.sqlite3-shm
backups/
```

不得继续把数据库可用性完全依赖可能变化的 Electron 产品名目录。

首次启用固定目录时：

1. 检查固定目录数据库；
2. 不存在时检查旧 `app.getPath('userData')/management.sqlite3`；
3. 关闭旧数据库连接；
4. 使用 SQLite 安全备份或完整复制策略迁移；
5. 验证新数据库可打开、可登录；
6. 验证成功后才使用新路径；
7. 不删除旧数据库，保留回退副本。

## 11.2 凭据状态保护

### OWNER_PASSWORD_ACTIVE

更新不得修改：

- username；
- password_hash；
- password_salt；
- credential_state。

### INITIAL_PASSWORD_REQUIRED

更新不得使用新安装包初始凭据覆盖数据库中已有初始凭据。

### LEGACY

现有行为会使用新初始密码覆盖旧密码，必须改为：

- 保留旧 password_hash；
- 保留旧 password_salt；
- 使用确定的管理员用户名补齐 username；
- 迁移为可登录状态；
- 原旧密码继续有效。

如果旧系统没有用户名，使用当前管理端固定管理员用户名或构建时明确的初始用户名，但不得替换旧密码。

## 11.3 初始凭据边界

安装包内置初始管理员凭据只允许用于：

```text
全新空数据库
```

不得用于：

- 覆盖已激活管理员；
- 覆盖已有初始管理员；
- 覆盖旧管理员密码；
- 数据库迁移失败后的自动重置。

## 11.4 迁移备份

每次数据库 Schema Migration 前：

```text
关闭写事务
→ 创建时间戳备份
→ 校验备份可打开
→ 执行 Migration
→ 运行完整性检查
→ 成功后启动服务
```

Migration 失败：

- 回滚事务；
- 保留原数据库；
- 不启动局域网业务服务；
- 显示明确错误；
- 不建立空数据库；
- 不重置管理员账号。

## 11.5 受保护发行字段

以下字段修改必须触发数据目录兼容审计：

```text
management/package.json name
build.appId
build.productName
```

Codex 本次不得修改这些字段。
