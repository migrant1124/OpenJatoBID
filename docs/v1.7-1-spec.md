# OpenJatoBID v1.7-1 上游能力选择性吸收实施规格

## 0. 文档用途与审批边界

本规格把用户确认的九项上游更新转换为可独立实施、验证、Review 和提交的小范围变更。`v1.7-1` 是本轮规划批次标识，不在本规格阶段修改 `client/package.json` 版本、创建分支、提交、合并、Tag、Release 或部署。

本规格批准前只允许分析和文档调整；批准后仍须按单项执行，每完成一项立即停止新增功能，完成该项 Review 后再交由用户决定是否提交和是否进入下一项。

## 1. 基线与吸收原则

### 1.1 核对基线

- 主项目分析基线：`OpenJatobid/main = 43711df`。
- 源项目分析终点：`OpenBidKit_Yibiao/main = f0eb5df`。

- 本规格只借鉴列明提交中的设计与修复，不执行整段合并、整提交 cherry-pick 或目录覆盖。

### 1.2 已核实的主项目现状

1. `adm-zip@0.5.17` 是主项目直接依赖，并被 DOCX 元数据读取、ZIP Markdown 解析、Agent 工具解压和 DOCX 导出测试真实调用。
2. `taskService.cjs` 已统一管理后台任务，但普通 checkpoint 仍会通过 Store 回读完整业务状态；标书查重进度更新尤其容易反复重建大快照。
3. `duplicateCheckStore.cjs` 已拆表存储，但部分读取路径会重复查询文件状态、加载分析明细，进度更新后还会完整 `loadDuplicateCheck()`。
4. `rejectionCheckStore.cjs` 的文档保存仍在 SQLite transaction 回调内执行同步文件写入，事务持锁时间包含文件系统耗时。
5. 正文页已有单小节重新生成入口，但“批量生成部分失败 → 只重试失败小节 → 继续既有正文审计和配图链”尚未形成明确稳定门禁。
6. Agnes 已作为生图服务商存在，但仍按通用 OpenAI-compatible 协议处理，未区分 Image 2.0/2.1 的请求、尺寸和比例规则。
7. 主项目没有 ComfyUI provider、统一存储清理服务或 OpenXML helper。

### 1.3 通用实施规则

- 保留主项目的授权、Analytics、AI 全局队列、技术方案 Guard、SQLite 权威状态、正文审计和图片编排链。

- 外部 API、文件系统、SQLite、原生 helper 和清理操作必须保留必要的错误处理与恢复证据。
- 新增后台 AI 请求继续通过 `aiService.cjs` 的既有队列和统计出口；不得绕过主项目埋点。
- 每项 Review 通过前不得开始下一项；Review 不自动授权 `git commit`。

## 4. U02：标书查重大文档性能优化

### 4.1 目标行为

在不改变查重算法输出语义、任务签名、结果结构和页面显示的前提下，减少大文档、多文档查重中的重复 SQLite 查询、重复 Markdown 读取、完整状态重载和不必要的中间字符串构造。

### 4.2 实施要求

1. 一轮查重开始时加载并缓存本轮必要的文件元数据；内部阶段不得为取得文件数或文件名反复调用完整 `loadFiles()`。
2. 每份已提取 Markdown 在需要正文时最多读取一次；只需要元数据的路径不得加载正文。
3. Store 加载函数允许显式选择是否包含大文本，不以默认全量读取满足轻量状态查询。
4. 正文分句和重复判定热路径采用单次线性扫描或等价低分配实现；判定规则和结果排序保持不变。
5. 进度更新只写当前 section 的变更字段，不因 `progress/message` 变化删除并重建其他 section 结果。
6. 保留输入 signature 和 stale-result 防护；新文件集合开始后，旧任务不得覆盖新结果。
7. 开发日志只记录文件数、字符数、阶段耗时、读取次数和结果计数，不记录正文、文件名或路径。

### 4.3 主要范围

- `client/electron/services/duplicateCheckService.cjs`

- 对应聚焦测试文件

## 7. U05：文件读写移出 SQLite 事务

### 7.1 已确认问题

`rejectionCheckStore.cjs` 当前在 `updateRejectionCheckTransaction` 内调用 `saveDocument()`，后者执行目录创建、临时文件写入和 rename；SQLite transaction 因此持锁等待文件系统。

### 7.2 目标结构

```text
按内容 hash 写入新的版本化文档路径
→ 执行只包含 SQL 的短事务，把记录切换到新路径/hash/计数
→ 事务成功后异步清理旧文件和导入图片
```

### 7.3 实施要求

- 仅先修 `rejectionCheckStore.cjs` 已确认路径，不复制源项目对知识库的大规模删改。
- 文件写入使用同目录临时文件和 rename，目标为包含内容 hash 的新路径；更新同一 document ID 时不得覆盖旧记录当前指向的文件。
- SQLite 只保存成功落盘后的新路径。DB 提交失败时删除本轮新路径，旧数据库记录和旧文件保持不变。
- 删除业务记录时先完成 DB 状态变化，再执行可重试的异步文件清理；清理失败留下孤儿文件而不是损坏业务状态。
- transaction 回调中不得出现 `readFile*`、`writeFile*`、`rename*`、`rm*`、`unlink*` 或图片目录遍历。

### 7.4 主要范围

- `client/electron/services/rejectionCheckStore.cjs`
- `client/electron/utils/importedImages.cjs`（仅在需要异步清理函数时）
- 废标检查 Store 聚焦测试

### 7.5 验收与 Review：REV-05

- 文件成功/DB 成功、文件失败、DB 失败、旧资源清理失败四条路径都有测试。
- 故障注入覆盖“更新既有同 ID 文档、文件新版本已落盘但 DB 提交失败”，并证明旧记录仍读取旧内容。
- DB 失败后旧文档仍可读取，新孤儿文件被安全回收。
- 中文路径和 Windows rename 行为通过测试。
- Review 重点：数据丢失风险、清理目标是否精确、transaction 是否真正不含文件 I/O。本项使用独立只读 Reviewer。

## 8. U06：正文失败小节单独重试并接回审计链

### 8.1 产品规则

1. 正文并发生成结束后，只要存在失败或未完成的 AI 小节，就停在稳定的“等待处理”状态。
2. 已成功小节和正文内容保持不变；不得因为少数失败重新生成全篇。
3. 用户可以重试全部失败小节，也可继续使用现有单小节重新生成入口处理指定失败小节。
4. 失败小节全部成功前，不得进入最低字数补足、原方案覆盖审计、全文一致性审计、图片编排或图片生成。
5. 最后一个失败小节成功后，从正文审计链尚未完成的第一个阶段继续，不重复已完成阶段。
6. 本轮不增加“忽略失败继续”入口，避免把缺失正文带入审计和导出。

### 8.2 状态要求

- runtime 明确记录失败小节 ID、等待处理状态和已完成阶段；ID 只保存在本地业务 Store，不进入 Analytics。
- 重试只选择 `error` 或中断后未完成的小节；已成功小节不得进入请求队列。
- 失败重试仍使用保存的正文生成选项、章节写作合同、知识库引用和全局事实。
- 页面卸载或应用重启后仍显示可重试状态，不把它误判为普通 idle 或完整成功。

### 8.3 主要范围

- `client/electron/services/contentGenerationTask.cjs`
- `client/electron/services/taskService.cjs`
- `client/electron/services/technicalPlanStore.cjs`
- `client/src/features/technical-plan/pages/ContentEditPage.tsx`
- 必要的 IPC 类型和聚焦测试

### 8.4 验收与 Review：REV-06

- 注入一个失败小节后，其他成功正文不变，后续审计和配图未启动。
- 重试请求只包含失败小节；成功后只运行尚未完成的后处理阶段。
- 重启恢复、暂停恢复、单小节重新生成和全文重新生成互不混淆。
- 埋点只记录重试动作和数量，不记录章节 ID、标题或正文。
- Review 重点：是否绕过技术方案 Guard、是否重复审计、是否错误清空成功正文。

## 9. U07：ComfyUI 本地/局域网生图

### 9.1 范围

- 设置页新增 `ComfyUI（本地/局域网）` provider，默认地址 `http://127.0.0.1:8188`，不要求 API Key。
- 支持用户粘贴 ComfyUI `Save (API Format)` 工作流 JSON。
- 未提供工作流时，只根据 `/object_info` 中可用 checkpoint 组装受控的最小文生图工作流。
- 本轮不读取、不复用 ComfyUI 服务端历史工作流；局域网服务可能包含其他用户的 prompt、模型路径和自定义节点，除非以后单独确认信任模型，否则不得启用。
- 仅支持文生图；本轮不支持 img2img、ControlNet、自定义节点参数面板或工作流编辑器。

### 9.2 实现约束

- ComfyUI 协议逻辑放入独立 `comfyUiImageProvider.cjs`，`aiService.cjs` 只负责选择 provider、队列、统计和统一返回值；不把源项目约 500 行实现整体塞入现有门面。
- 用户粘贴的工作流只允许本轮白名单节点类型，并必须存在 sampler、正向文本、latent 和图片输出节点；提示词不得写入 negative 节点。发现未知或自定义节点时拒绝执行并提示用户。
- 第一版允许的 `class_type` 固定为：`CheckpointLoaderSimple`、`CLIPTextEncode`、`EmptyLatentImage`、`EmptySD3LatentImage`、`KSampler`、`KSamplerAdvanced`、`VAEDecode`、`SaveImage`。
- 各节点只允许以下 `inputs`：loader 的 `ckpt_name`；CLIP 的 `text/clip`；latent 的 `width/height/batch_size`；sampler 的 `model/positive/negative/latent_image/seed/noise_seed/steps/cfg/sampler_name/scheduler/denoise/add_noise/start_at_step/end_at_step/return_with_leftover_noise`；VAE decode 的 `samples/vae`；SaveImage 的 `images/filename_prefix`。节点链接数组可以透传；未知字段一律拒绝。程序只改正向 `text`、合法尺寸、数值 seed/noise_seed 和固定 `filename_prefix`，其他白名单字段保持用户值。
- 尺寸限制在 `64..8192` 且为 8 的倍数；seed 若为节点链接则保留链接，只随机化数值 seed。
- `/prompt` 提交是非幂等操作，提交失败不得自动重试；只允许对状态轮询和图片下载的瞬时失败做有界重试。
- 任务进入终态但没有图片时立即报错，不继续无意义轮询。
- 继续使用现有生图并发队列、图片落盘、开发日志和 Analytics；日志不得记录完整工作流、prompt 或局域网地址。

## 10. U08：安全的存储清理

### 10.1 清理范围

1. 一次性历史清理：`<userData>/workspace/technical_plan.json`、`duplicate_check.json`、`rejection_check.json` 三个已明确不再读取的旧状态文件，以及当前源码没有调用者的 `<userData>/agent-cache/` 整个旧缓存目录。
2. 启动期轻量清理：`<userData>/workspace/generated-images/` 根目录中符合当前生图命名规则且数据库无引用的文件。`<userData>/agent-runtime/pi/` 下的 service workspace、tmp 和任务归档全部排除；它们可能是尚未进入业务 Store 的唯一 Agent 输出或失败恢复证据。
3. 更新安装包：只匹配 `<userData>/updates/Jato-AI-BID-<version>-win-x64.exe` 或 `Jato-AI-BID-<version>-mac-(x64|arm64).dmg`，仅删除版本小于或等于当前已安装版本的文件。
4. 数据库备份：只匹配 `<userData>/workspace/yibiao.sqlite.backup-<timestamp>`、`yibiao.sqlite-wal.backup-<timestamp>`、`yibiao.sqlite-shm.backup-<timestamp>`；数据库迁移成功且当前数据库健康检查通过后，按共同 timestamp 分组并保留最近 3 组，删除更旧完整组，不照搬源项目“删除全部备份”。

### 10.2 安全边界

- 新增版本化 `storage_cleanup_version`；历史清理全部成功后才能写完成标记，失败时下次启动重试。
- 所有删除目标必须由固定 `userData` 子路径和文件名规则解析，禁止接受 Renderer 传入路径、通配根路径或用户文件名。
- 不自动清理 `<userData>/agent-runtime/`。只有未来能逐任务证明结果已进入业务 Store、没有路径引用且具备恢复方式时，才能另立规格增加精确的 Agent 清理规则。
- 删除生成图片前，必须同时查询图片计划和正文中的有效 `yibiao-asset://generated-images/...` 引用；有任何引用、文件名不符合 `saveGeneratedImage()` 现行时间戳加 UUID 规则、或文件位于子目录时一律保留。
- 旧 JSON 与 `agent-cache` 只在首次历史清理删除；恢复依赖清理前仍保留的 SQLite 和现行 Agent runtime，不把旧 JSON/cache 当恢复源。
- 更新包可由更新服务重新下载；数据库旧备份的恢复来源是保留的最近 3 组。无法明确写出恢复方式的路径不得加入自动清理。
- 永不删除当前 `yibiao.sqlite`、当前 WAL/SHM、`user_config.json`、知识库原文、当前技术方案 Markdown、导出文件、有效 Agent 工作区或用户选择的源文件。
- 清理失败不得阻止启动；记录本地开发日志和计数，不记录文件名、完整路径或业务内容。
- 不新增普通用户清理 UI；本轮只处理可确定安全删除的缓存。
