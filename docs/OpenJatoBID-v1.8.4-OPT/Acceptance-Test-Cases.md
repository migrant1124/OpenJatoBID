## 执行与判定

每个用例登记PASS / FAIL / NOT_RUN / BLOCKED，注明实际提交或工作区指纹、系统、两端版本、依赖版本、命令、退出码及证据路径。P0未通过不得宣称本轮全部完成；受环境限制未执行须明确标注，不可默认通过。P1中本轮核心视觉偏差也必须修复后才能声称“已按图实现”。

用可控适配器/伪时钟/故障注入验证去重、周期和边界，同时用真实Windows安装包验证完整链路。fixture仅是测试输入，不得进入生产数据或充当真实已发布资源。离线和模型测试必须记录网络拦截或实际调用，不得只依据按钮文字。

UI编号对应UI-State-Matrix；一个编号可有多个结果分支。所有编号均须登记真实截图及状态覆盖，不把通用弹窗截图复制成不同业务已通过。

## 必须分开的验证层级

| 层级 | 最低验证内容 | 能证明什么 / 不能替代什么 |
|---|---|---|
| 静态与单元 | TypeScript、Main语法、纯函数、伪时钟、差异计算、迁移 | 不证明真实文件下载或Office排版 |
| Renderer / IPC集成 | checkbox草稿、弹窗、会话问答、权限与事务 | 不证明安装包固定组件完整 |
| SDK与代理 | 真实选定Pi/模型SDK、消息与工具schema、question路由、费用去重 | 不用普通HTTP mock冒充真实渠道兼容 |
| Electron / 两端联调 | 原生文件选择、IPC、SQLite、受控runtime、LAN | 不等同干净系统安装测试 |
| Windows安装 | 本地独立测试包、中文路径、125%缩放、重启恢复 | 不等同PowerPoint/WPS成品视觉验收 |
| 成品验收 | PPTX/PDF/图片/讲稿、对象编辑及Office/WPS目视 | 结构通过与视觉通过分别记录 |

执行命令先检查实际package.json。取证基线客户端存在`npm run build`和`npm run test:ci-upgrade`，不能凭空要求不存在的通用`npm test`。管理端用现有`npm test`、`npm run build`。本轮新增用例按项目现有runner执行；涉及Main/preload运行`node --check`。运行测试前妥善保护真实userData和私有凭据。
