# OpenJatoBID v1.4.1 OpenCode 隔离与知识库超长文件适配规格

## 1. 文档目的

本规格用于指导 Codex 将本地 `upstream-main` 中已经完成的两组能力，适配到 OpenJatoBID 的 `main`：

1. OpenCode 逻辑隔离。
2. 知识库超长文件分段分析与提示词缓存优化。

本地仓库中的：

```text
upstream-main
```

已经是最新版源代码分支。Codex 必须直接以本地 `upstream-main` 为上游代码基线进行差异分析，不需要再次从远程源仓库抓取代码，也不得使用旧 Tag、旧 Patch 或旧分析文档代替当前本地分支。

本次采用：

```text
以 main 为产品基线
以 upstream-main 为功能参考
按函数和能力进行语义移植
```

禁止整分支合并和整文件覆盖。

## 2. 已确认实施范围

本规格只包含下列已确认项目。

### 2.1 OpenCode 逻辑隔离

- A1：建立独立 HOME、Config、Cache、Data、State、Temp。
- A2：不继承员工电脑的 OpenCode 用户配置和项目配置。
- A3：收窄 PATH，只使用系统基础路径和应用打包工具。
- A4：禁止外部插件。
- A5：禁止 MCP。
- A6：禁止远程 Skill。
- A7：禁止访问工作区外目录。
- A8：OpenCode 启动前执行 CLI 隔离预检。
- A9：OpenCode Server 启动后复核实际生效配置。
- A10：隔离失败时不启动 Agent Runtime。
- A11-2：只允许 OpenJatoBID 安装包中明确指定的内置 Skill。
- A12-1：隔离失败只禁用 Agent；客户端其他功能继续使用。

### 2.2 知识库超长文件处理

- B1：按当前文本模型上下文自动分段。
- B2：请求上下文预算比例为 80%。
- B3：任务说明和知识条目预留比例为 20%。
- B4：连续 Block 打包。
- B5：知识条目过长时再分子批。
- B6：第一轮知识条目提取支持分段。
- B7：补充遗漏知识条目支持分段。
- B8：条目与 Block 匹配支持分段。
- B9：未归属 Block 补漏支持分段。
- B10：多段结果统一合并。
- B11：每个 Block 只能有一个最终归属。
- B12：归属优先级为 `matches > new_items > discarded`。
- B13：Prompt 使用稳定的 Block 前缀。
- B14：首轮请求后固定等待 5000ms，再展开后续并发请求。
- B15：保留 IPC 中的 `batchSize` 参数，但服务端忽略该参数。
- B16：删除知识库页面中的手工批次设置。
- B17-1：并发分段使用 `Promise.allSettled()`；等待当前批次全部结束后，如有失败，抛出第一个失败。

> 编号约束：A11-2、A12-1、B17-1 均为已经确认的正式实施项，与 A1-A10、B1-B16 具有相同强制级别，必须编码、测试和验收，不得降级为说明、建议或异常场景备注。

# 第一部分：OpenCode 逻辑隔离

## 6. 目标

确保客户端内嵌 OpenCode：

- 不读取员工电脑上的个人 OpenCode 配置。
- 不读取其他项目的 OpenCode 配置。
- 不加载外部插件、MCP 或远程 Skill。
- 不加载未经 OpenJatoBID 明确允许的本地 Skill。
- 不访问当前任务允许目录之外的文件。
- 只调用应用打包的工具和系统基础命令。
- 启动前和启动后都能验证隔离真实生效。
- 隔离失败时只禁用 Agent，不影响客户端其他功能。

## 11. 内置 Skill 白名单

### 11.1 允许范围

客户端内嵌 OpenCode 只允许加载：

```text

```

允许路径必须由应用代码或打包清单明确提供，不能通过扫描用户目录自动发现。

### 11.2 禁止范围

必须拒绝：

- 其他项目目录中的 Skill。
- `.opencode` 或 `.config/opencode` 中的 Skill。
- 远程 Skill URL。
- 未在 OpenJatoBID 内置允许根目录中的 Skill。
- 运行时临时下载的 Skill。

### 11.3 与开发 Skill 的边界

本项只约束：

```text
客户端内嵌 OpenCode Agent Runtime
```

不影响开发人员在 Codex 中调用的项目开发 Skill。

## 12. 允许目录

环境准备函数至少应返回：

```text
allowedRoots
skillRoots
mutableRoots
permissionExceptionRoots
```

语义：

- `allowedRoots`：OpenCode 可以读取或使用的总体根目录。
- `skillRoots`：允许加载 Skill 的根目录。
- `mutableRoots`：OpenCode 可以创建运行数据的根目录。
- `permissionExceptionRoots`：在全局外部目录拒绝规则后允许的最小例外目录。

允许目录必须使用规范化绝对路径。

Windows 下路径比较必须忽略盘符和大小写差异。

---

## 13. 启动前 CLI 隔离预检

OpenCode Server 启动前执行：

```text
opencode debug paths --pure
opencode debug skill --pure
```

### 13.1 路径检查

必须检查：

```text
home
data
bin
log
repos
cache
config
state
tmp
```

要求：

- 所有可变路径位于 `mutableRoots` 内。
- HOME 等于预期隔离 HOME。
- Config 等于预期隔离 Config。
- 任何路径越界均视为失败。

### 13.2 Skill 检查

- 无文件位置的内建项可以保留。
- 带文件位置的 Skill 必须位于 `skillRoots`。
- 发现外部 Skill 即失败。

### 13.3 超时

预检必须有固定超时，使用上游现有值：

```text
15 秒
```

超时、进程无法启动、输出无法解析或路径不符合预期均视为隔离失败。

---

## 14. Server 启动后复核

OpenCode Server 健康检查通过后，读取：

```text
/path
/config
/skill
/agent
```

### 14.1 路径复核

验证：

- `directory` 等于当前任务工作区。
- `worktree` 不越界。
- `home` 等于隔离 HOME。
- `config` 等于隔离 Config。
- `state` 等于隔离 State。

### 14.2 配置复核

最终配置必须满足：

- `plugin` 为空。
- `plugin_origins` 为空。
- `mcp` 为空。
- 远程 Skill URL 为空。
- Skill 路径全部属于 `skillRoots`。
- Instructions 只来自 OpenJatoBID 允许路径。
- Shell 等于应用配置的可信 Shell。
- Provider 和 Model 未被外部配置污染。
- `external_directory` 最终权限为 `deny`。

### 14.3 Agent 权限复核

每个 Agent 都必须存在：

```text
external_directory * deny
```

该拒绝规则之后只允许：

- 继续拒绝。
- 对 `permissionExceptionRoots` 中的明确目录放行。

任何其他放行均视为越界。

Agent Runtime 不启动或立即关闭

### 16.3 设置页

在现有“智能体配置”自检结果中增加隔离检查状态。

不得整文件覆盖 `SettingsPage.tsx`。

# 第二部分：知识库超长文件处理

- 条目与正文 Block 匹配。
- 未归属 Block 补漏。
- 多段结果合并。
- Block 唯一归属。

用户不再手工控制批次大小。

## 20. 消息长度预算

新增或适配：

```js
getMessagesContentLength(messages)
```

用于估算：

- role 长度。
- content 长度。
- 每条消息固定开销。

知识库单次请求预算：

```text
requestBudget = contextLengthLimit × 0.8
```

文档 Block 预算还必须预留 20% 给：

- 任务说明。
- 知识条目。
- JSON 格式约束。
- 消息结构开销。

若 `aiService.getConfig()` 不存在、返回无效值或上下文长度小于等于 0，使用：

```text
400000
```

## 21. Block 分段

新增或适配：

```js
packBlocksIntoSegments(blocks, segmentLimit)
```

要求：

- 保持原 Block 顺序。
- 按 `renderBlocksForPrompt()` 后的实际字符长度计算。
- 优先在 Block 边界切段。
- 正常情况下不拆分单个 Block。
- 每段返回：

```ts
{
  blocks,
  blockIds,
  text,
  chars,
  index,
  total
}
```

- 空输入返回空数组。
- `segmentLimit` 无效时规范化为最小正值。
- 不得丢失 Block。
- 不得重复 Block。

## 22. 知识条目分段

新增或适配：

```js
packItemsIntoSegments(items, segmentLimit)
```

仅在完整知识条目集合无法和当前 Block 段共同放入上下文时启用。

要求：

- 保持条目顺序。
- 按序列化后的 JSON 长度打包。
- 每段包含条目和条目 ID。
- 不得丢失或重复条目。

---

## 23. 分段覆盖阶段

以下阶段必须支持多段：

### 23.1 初次提取

对每个 Block Segment 提取：

```json
{
  "items": [
    {
      "title": "",
      "summary": ""
    }
  ]
}
```

分段结果通过：

```js
mergeTitleSummaryItems()
```

合并，并按规范化标题去重。

### 23.2 补充遗漏条目

以完整首轮条目作为任务后缀，对相同 Block Segment 再次检查遗漏。

新增结果不得重复首轮条目。

### 23.3 条目匹配

对 Block Segment 和知识条目批次进行匹配，输出：

```json
{
  "matches": [
    {
      "id": "K000001",
      "ranges": [
        ["P000001", "P000003"]
      ]
    }
  ]
}
```

多段结果通过：

```js
mergeMatchResults()
```

合并。

### 23.4 未归属 Block 补漏

每个未归属 Block 必须进入以下三类之一：

```text
matches
new_items
discarded
```

输出结果必须覆盖收到的全部遗漏 Block。

---

## 24. Block 唯一归属

合并补漏结果时使用固定优先级：

```text
matches
> new_items
> discarded
```

要求：

1. 先处理 `matches`。
2. 再处理 `new_items`。
3. 最后处理 `discarded`。
4. 一个 Block 一旦被高优先级结果认领，低优先级结果不得再次认领。
5. 合并后重新根据最终 `block_ids` 生成 `ranges`。
6. 不得信任冲突结果中的原始 `ranges` 作为最终权威数据。
7. 最终每个 Block 最多只属于一个结果。

使用或适配：

```js
mergeRecoverySegmentResults()
```

## 27. 分段并发和失败行为

使用等价实现：

```js
async function runParallelAndThrowAfterSettled(taskFns) {
  const results = await Promise.allSettled(taskFns.map((fn) => fn()));
  const rejected = results.find((item) => item.status === 'rejected');
  if (rejected) throw rejected.reason;
  return results.map((item) => item.value);
}
```

要求：

- 当前批次已开始的分段全部结束后再处理失败。
- 存在多个失败时抛出第一个失败。
- 不因首个失败立即取消其他已开始分段。
- 所有请求继续走 `main` 现有 AI Service 和全局并发队列。
- 不绕过文本模型 `concurrency_limit`。
- 暂停和用户取消继续使用 `main` 现有机制。
