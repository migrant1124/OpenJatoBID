```text
约束：保持 6 个普通主菜单加底部设置；不把浏览器 mock 验证冒充 Electron/IPC 验证。优先用当前可用的 Chrome DevTools MCP 做界面核验，需要可重复脚本时复用 Playwright。工具不可用就明确说明并采用已有可行检查，不声称调用过不可用工具。

第四步：网络与数据兼容。
输入：网络记录、共享统计测试、经授权的一致性旧工作区副本。
输出：退役资源页接口无页面调用、保留网络链路正常、历史业务数据稳定字段及引用关系正确的证据。
约束：不封整个域名、不上传客户原文/密钥、不改 analytics/ 或 management/；不清空生产 userData。未获授权的生产数据不用于测试；没有合格副本则记录阻塞。

第五步：构建产物和本地验证包。
输入：本轮构建的 JS/CSS 与可用的 Windows 本地打包环境。
输出：无删除页独占模块/专用样式的产物核验，以及验证包启动、导航、模板导出结果。
约束：本地 electron-builder 必须使用 --publish never。不得触发 Actions、创建 Release、上传 R2、读取发布私钥或安装到正式员工环境。环境不足则明确“未完成安装包验收”，不得把源码构建通过当作可发布。

第六步：版本一致性与分支边界。
输入：实际客户端/锁文件版本字段、既有版本显示位置、本地验证包、开始时的分支/HEAD 记录和本轮 diff。
输出：规格 TC26/TC27 的证据：目标版本 1.8.4，管理端版本及依赖树不变，既有显示链路与验证包版本正确，起止实施分支一致且无未授权 Git 操作。
约束：静态、Electron 显示和打包验证分别记录，不硬编码测试结果；没有运行时或包证据就标未执行，不以 package.json 正确代替全部验收。发现错版本只记录，返回 Build 修复，不在 Verify 阶段改文件。

输出报告：
docs/secondary-development/test-reports/v1.8.4-feature-pruning-test-report.md。
记录目标客户端版本 v1.8.4、实际版本字段/显示/产物结果、执行时间、工作目录、实际实施分支、HEAD 和差异标识、工具版本、命令、退出码、用例 ID、实际结果、证据位置、覆盖深度和未测项。tasks/todo.md 仍是唯一任务状态源。

每个用例使用：通过 / 失败 / 未执行 / 环境阻塞。新增问题、既有问题和环境问题分开。未测不等于通过，未发现源码引用不等于运行验证完成。
不要自动用真实收费模型重跑长篇生成，不伪造节省时间或安装包缩小比例。完成后给出代码实现、测试完成、可发布验收三个独立结论，并停止，不修改源码或发布。
```

这段指令的作用：让 Codex 拿出证据，而不是只说“编译过了，所以没问题”。没有条件测试的项目必须明确写出来。

## 五、指令四：最终只读 Review

### 输入

规格、技术计划、全部本轮差异、原有改动记录及测试证据。

### 输出

按严重程度排列的审查结果，以及是否满足本轮规格的结论。

### 关键约束

不在 Review 阶段直接修改代码。能使用独立 Reviewer 时使用，不能使用时明确披露。

**可直接复制：**

```text
$openjatobid-secondary-development review：

只读审查“v1.8.4 功能精简”，不修改源码、测试、配置或 Git 状态。复用用户现有实施分支，不创建、切换或重置；核对起止分支、HEAD 和操作记录。

输入：
- docs/secondary-development/prd/v1.8.4-feature-pruning-spec.md。
- tasks/plan.md、tasks/todo.md 的本轮部分。
- 全部实际改动，包括未跟踪但属于本轮的新测试文件；与最初用户原有改动分开。
- docs/secondary-development/test-reports/v1.8.4-feature-pruning-test-report.md 及其证据。

按以下步骤审查：

第一步：需求与差异一致性。
输入：删除清单、保护清单、实际 diff。
输出：逐项说明是否漏删、误删或扩大范围。
约束：不能把可选的真实功能删除、侧栏下沉或依赖裁剪当作已授权需求。

第二步：关键风险检查。
输入：菜单、路由、模板、CSS、统计与数据相关引用。
输出：确认 8 个目标入口不再加载独占页面；普通用户菜单不变；4 个开发者入口仍在；export-format 没有误伤模板；没有删除共享 Analytics、Word 导出、知识库、图片、Agent 或任务服务。
约束：允许有证据的历史统计/兼容残留，不以字符串零命中作为唯一标准。

第三步：验证证据真实性。
输入：测试报告与实际日志、截图、产物。
输出：区分已验证、仅源码判断、仅浏览器 mock、未执行和环境阻塞；核对安装包/旧数据/真实导出结论。
约束：不把“文件未改”当作测试通过，不接受捏造的性能收益，不因缺证据自行补写“通过”。

第四步：交付审查。
输入：当前分支与差异、受保护目录、版本和锁文件。
输出：确认客户端根项目版本字段一致为 1.8.4，管理端版本和锁文件依赖树不变，实际版本显示/产物结论有证据；确认复用用户已建分支，没有越界修改或未经授权的分支操作、提交、推送、tag、发布；给出当前能交付什么、还缺什么。
约束：按规格第 0.2 节区分允许的版本字段修改与依赖升级，不再用旧版“版本号一律不变”判定；Review 不修代码，不执行 Git 写操作。

优先使用项目已有 openjatobid_reviewer 做独立只读审查；不可用时说明“本次不是独立上下文审查”，再在当前会话按同样标准执行，不声称已调用。

报告写入：
docs/secondary-development/reviews/v1.8.4-feature-pruning-review.md。
每个问题包含严重程度、文件及行号、证据、用户影响和最小修复建议。先列问题，再列结论；没有问题也要说明实际审查范围与剩余验证限制。

对范围内缺陷列出返回 Build 的任务；对新功能或扩大删除范围只列建议，不实施。最终停止，不提交、不合并、不推送、不打 tag、不发布。
```

这段指令的作用：从规格和证据反查实现，重点查“有没有删错”和“有没有把没测过的说成测过了”。

## 六、指令五：仅修复本轮范围内问题

### 输入

Review 或 Verify 的具体问题、已批准计划、当前差异。

### 输出

最小修复、对应测试和任务记录更新。

### 关键约束

只处理原范围内缺陷。需要改变产品行为或扩大范围的问题，不属于自动修复授权。

**需要修复时复制：**

```text
$openjatobid-secondary-development build：

修复“v1.8.4 功能精简”在最近 Verify/Review 中发现的、属于已批准规格和技术计划范围内的问题，不实施新增功能或扩大删除范围的建议。只读核对并复用用户现有实施分支；不创建/切换/重置分支。分支与已确认计划不符时停止源码修改并说明。

输入：
- docs/secondary-development/prd/v1.8.4-feature-pruning-spec.md。
- tasks/plan.md、tasks/todo.md。
- 最新 v1.8.4-feature-pruning-test-report.md 和 v1.8.4-feature-pruning-review.md 的具体问题及证据。
- 当前源码和原有用户改动保护记录。

第一步：把问题分为“本轮范围内缺陷”“既有问题”“环境阻塞”“需要新产品决策”。
输出：本次确实要修的具体问题及文件。约束：后两类不靠改业务或降低验收标准强行解决；超范围先进入 Change，不实施。

第二步：只对本轮范围内缺陷做最小修改。
输出：对应源码/测试修复；属于规格第 0.2 节白名单的漏改或错改版本字段可修正到 1.8.4。约束：保留正常菜单、模板、全部真实业务、共享统计与数据；不改成其他版本、不升级依赖、不改管理端版本或发布/授权逻辑，不增加兜底框架、不覆盖用户原改动。

第三步：运行每项修复直接相关的测试及客户端构建。
输出：真实命令、退出码、前后问题状态和证据。约束：禁止删测试、关断言、吞异常或篡改报告；旧报告标明被哪次复验取代，不悄悄改成通过。

任务状态只更新 tasks/todo.md 的本轮部分，并更新必要证据。不得创建/切换/重命名/删除分支，不得执行 switch、checkout、add、commit、push、pull、fetch、merge、rebase、reset、clean、stash、tag、npm version 或发布动作。

完成后说明哪些问题已修、哪些仍阻塞，并返回 Verify 和 Review，不宣称未经验证的全部完成。
```

这段指令的作用：让修复仍然被原范围约束，避免发现一个问题后顺手重构整个项目。

## 七、用户查看计划和最终结果时的判断标准

### 技术计划可以接受的核心条件

| 检查点 | 应看到什么 |
| --- | --- |
| 范围 | 8 个固定入口加两项辅助清理，没有新增真实业务删除 |
| 文件 | 每个被删文件都有所属功能和引用证据，而不是整目录模糊删除 |
| 模板 | 明确保留 `features/export-format/` 和 Word 导出，旧 ID 有 A/B/C 结论 |
| 统计 | 删除资源页但保留共享埋点、历史映射、管理端和统计后端 |
| 界面 | 普通用户 7 个一级入口不变，开发者测试页只减少三个演示子入口 |
| 数据 | 不清空工作区、不改数据库结构、不覆盖用户原修改 |
| 验证 | 有实际菜单行为、Electron、模板导出和产物测试，不只有编译 |
| 版本 | 客户端根项目版本为 1.8.4，锁文件只变根项目版本字段；管理端及第三方依赖不变 |
| 分支 | 记录并复用用户已建分支，不出现创建/切换分支或 npm version 等隐式 Git 操作 |

### 最终交付必须能回答的问题

你应能看到：具体删了哪些文件；哪些同名或共享代码刻意保留；正常业务怎样验证；客户端版本是否一致为 1.8.4；是否复用用户已建分支；哪些测试没做及原因；当前代码是否只是本地未提交；是否存在发布前阻塞。

如果 Codex 声称“已经删除知识库/查重/扩写”“顺便合并了侧栏”“顺便升级了依赖”“数据库重置后正常了”或“安装包没测但可以发布”，都不符合本轮规格。

本轮没有预定节省时间或体积百分比。真实收益首先是移除废弃代码和降低维护风险，数量化指标必须有测量环境和前后结果。

**一句话总结：这套指令让 Codex按“先核对、经确认再删、拿证据验收、只读复审”的顺序实施精简，减少误删共享功能和未经确认扩大改动的风险。**
