# ADR：Markdown 格式要求驱动的目录与人工填写节点

- 状态：Accepted
- 日期：2026-07-13
- 修订：2026-07-13，原结构化 profile、来源锚点与固定模板方案由 CHG-001 替代
- 需求基线：`docs/secondary-development/changes/format-requirements-simplification-change.md`
- 适用范围：`client/`；不修改 `management/`、Analytics、依赖或发布流程

## 背景

`upstream-main` 的 `responseFileRequirements` 是可选 Markdown 解析项，只负责提取响应/投标文件组成、格式模板、签章和递交要求。旧目录生成任务只读取项目概述和技术评分要求，因此“响应文件要求”本身不会影响一级目录。

上一版设计新增 `bidDocumentFormatRequirements` 严格 JSON 任务、来源锚点、多 profile、固定模板编译、目录锁定和六种响应模式。真实样本持续在 Step02 出现锚点和来源校验失败。该问题不是某个锚点规则不足，而是业务语义提取与系统身份、逐字模板校验耦合。

用户已批准恢复 Markdown 任务，并重新定义一级目录来源与人工填写边界。

## 决策

### 1. 恢复 `responseFileRequirements`，Main 继续作为任务目录唯一权威

活跃关键项顺序为：

1. `projectOverview`：项目概述；
2. `techRequirements`：技术评分要求；
3. `responseFileRequirements`：格式要求；
4. `procurementList`：采购与报价；
5. `projectInfo`：项目信息；
6. `partAInfo`：甲方信息；
7. `deliveryAndServiceRequirements`：交货和服务要求。

`responseFileRequirements` 设置为 `required: true`、`output: 'markdown'`。Renderer 继续读取 Main 返回的任务元数据，不恢复第二份生产任务清单或 Prompt。

历史 `bidDocumentFormatRequirements` 和 `quotationRequirements` 数据保留但不显示、不计入关键项完成度，也不冒充当前任务成功结果。

### 2. 格式要求只提取业务语义

格式要求读取当前投标范围工作副本，沿用原响应文件要求的 Markdown 提取方式。它可以整理：

- 投标/响应文件组成；
- 技术文件明确目录及顺序；
- 固定表格、承诺函和附件名称；
- 文件命名、格式、份数、签章、装订、上传和递交规则；
- 必须提供与如适用内容。

模型不返回 profile、来源锚点、行号、excerpt、template ID、slot、cell 或锁定 Hash。格式任务只执行一次正常 Markdown 请求，不发起 JSON 修复或固定模板第二阶段请求。

为让 Step03 在目录请求前确定分支，Markdown 第一行固定为以下二选一状态，后续仍是普通可读 Markdown：

```text
【技术文件目录状态】：明确
【技术文件目录状态】：未明确
```

除该状态行外不建立新的结构化格式契约。状态缺失或非法时该项解析失败，由用户单项重试，不猜测分支。

### 3. 一级目录有且只有两个来源分支

目录生成前必须读取有效的格式要求 Markdown。

#### 有明确技术文件格式

- 一级目录按格式要求中的技术文件目录生成；
- 保留其标题、顺序、“如有”和“其他”等已列节点；
- 技术评分项只能映射或补充二级及以下目录；
- 所选知识库文档可作为二级及以下目录和描述的参考，不得覆盖一级目录。

#### 无明确技术文件格式

- 一级目录参考用户所选知识库文档的目录生成；
- 多份参考文档由 AI 综合为一套适合当前项目的目录；
- 技术评分项只能映射或补充二级及以下目录；
- 未选择任何知识库文档时阻止生成，禁止退回评分大类或通用目录。

阻断错误固定为：

> 招标文件未规定明确目录格式，请至少选择一份参考知识库文档后生成目录。

该规则同时适用于“生成技术方案”和“已有方案扩写”。已有方案内容仍可作为正文和下级目录参考，但不能改变上述一级目录来源规则。

### 4. 技术评分项只负责下级覆盖

技术评分要求继续用于：

- 建立评分要求分组；
- 映射到已有一级目录；
- 在一级目录下生成二级、三级及必要的四级目录；
- 检查每个技术评分项是否被某个下级节点覆盖。

技术评分项不能直接或间接新增一级目录。最终审查发现未映射评分项时，应在既有一级目录下补充，不得改变一级目录集合。

### 5. 固定表格和承诺函改为人工填写

目录输出仅增加：

```ts
manual_input_required?: boolean;
```

固定表格和承诺函节点设置为 `true`。该标记表达“保留目录、人工填写”，不表达模板锁定或逐字校验。

人工填写节点：

- 不进入批量正文生成；
- 不允许单节 AI 重生成、扩写或自动修复；
- 继续使用普通 Markdown 编辑器和普通保存；
- 正文为空时在导出前阻断并列出节点；
- 内容非空时允许导出，不比较招标原文，不计算固定内容 Hash。

普通节点由 AI 生成 Markdown，允许根据项目语境改写、扩写和专业化表达。

### 6. 复用 SQLite v18，禁止破坏性降级

不新增数据库版本，也不删除 v18 已有列和表：

- `selected_format_profile_id`、`selected_format_profile_hash`；
- `normalized_hash`；
- `format_constraints_json`、`response_state_json`；
- `technical_plan_response_templates`。

新路径只在既有 `format_constraints_json` 中持久化 `manual_input_required`，其余旧格式约束字段不再由新目录生成。旧 profile 和模板记录不再进入活跃业务流程。

这样可以避免工作区降级或删列，同时让新实现保持最小改动。

### 7. 失效规则保持直接

以下变化清理目录及后续正文状态：

- `responseFileRequirements` 内容变化；
- 有/无明确格式的判断变化；
- 无明确格式时所选参考知识库文档变化；
- 目录一级结构变化；
- `manual_input_required` 变化。

重新解析其他不影响目录的项目，不清理目录或正文。

## 被否决方案

- 恢复 `bidDocumentFormatRequirements` 结构化 JSON：已被真实样本证明职责过重。
- 继续修补来源锚点、连续性和表格分组：只处理旧架构表象。
- 无明确格式时按技术评分大类生成一级目录：违反已批准业务规则。
- 无知识库时自动生成通用一级目录：隐藏缺失输入，违反阻断要求。
- 通过标题关键字在正文阶段猜固定表格或承诺函：不稳定；应由目录生成显式返回 `manual_input_required`。
- 保留 slot/cell/模板 Hash：超出“保留目录、人工填写”的目标。
- 删除 SQLite v18 字段或降级数据库：会破坏已有工作区，且不是恢复简单业务行为所必需。

## 后果与风险

### 优点

- Step02 回到稳定的 Markdown 语义提取；
- 一级目录来源规则清晰且可向用户解释；
- 技术评分覆盖不再改变一级目录；
- 固定格式内容由用户负责，系统不再承担不可靠的逐字模板编译；
- 不需要数据库升级或依赖变更。

### 风险

- Markdown 格式要求不提供确定性来源证明，一级目录正确性仍需真实样本验收；
- 多份知识库目录的综合结果具有模型判断成分；
- 人工填写节点内容由用户负责，系统只检查是否为空；
- 旧架构代码需外科手术式退役，不能直接回退整个提交，以免覆盖同一提交中的有效功能。
