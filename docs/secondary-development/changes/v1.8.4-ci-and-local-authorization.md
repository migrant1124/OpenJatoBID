## 修改目的与范围

此前 CI184-F01 是本地 PPT 改动合入后缺运行包的打包阻塞；F02 是升级回归未入门禁；F03 是测试依赖本机临时输入。本轮修复这些问题，不修改授权规则、产品页面或发布资产/密钥协议。

- `.github/workflows/verify.yml`：main push、目标 main 的 PR 和手动验证，Windows 2022 两个独立 job；客户端 Node 26、管理端 Node 22，各用锁文件安装、离线回归、构建。仅 `contents: read`，不注入生产 Secret、不创建或上传安装包、不发布。
- `.github/workflows/release.yml`：仍只有手动发布，保持四个输入、tag/SHA/可信 main 历史、构建证明、NSIS `--publish never`、资产白名单、管理端私有 Draft/R2 与客户端 Worker/回滚门禁。客户端增加固定样本、Pi/PPT/授权离线回归、真实 Electron Pi/资源回归及 PPT prepare/verify。管理端新构建在打包前用 `npm ci --ignore-scripts` 安装客户端准备器依赖，独立生成 `--management` 预览运行包并校验；resume 跳过三个准备步骤。
- `.github/scripts/ci-upgrade-workflow.test.mjs`：保护自动验证无发布/凭据副作用、两端准备顺序和管理端 resume、固定测试输入，不放宽现有发布断言。
- `client/scripts/verify-packaged-ppt-runtime.cjs`：发布打包后、上传前用产物自己的 Electron 运行既有包内探针，核对 Pi/SQLite/生产依赖、逐文件 hash 与 AppContainer/Python 实际执行；管理端 resume 不重新运行新构建探针。
- `client/scripts/ppt-test-fixtures.json`、`prepare-ppt-test-fixtures.cjs`：从固定 wuhua commit 与固定 hash 的公开 free v3 样本获取原包。下载/内容变化失败即阻断，不取用任何员工资料，不承诺全库原生复用。
- `client/scripts/ppt-template.test.cjs`：默认使用 `.tmp/ci-ppt-fixtures`，可通过 `JATOBID_PPT_TEST_FIXTURES` 显式指定。既有真实样本断言保留。
- `client/scripts/ppt-ui-electron-smoke.cjs`：移除本机随机目录常量，两个位置参数要求本轮的预览、公开提示词证据；缺输入直接失败。没有用合成图片替代其真实来源验收。
- `client/scripts/lan-same-machine-electron-smoke.cjs`：两个真实 Main/preload/Renderer、HTTP 的可重复同机申请/审批/登录验证。合成初始凭据只注入测试启动壳；提前设置独立 userData、LOCALAPPDATA，关闭测试开机自启与资源自动下载。管理端 native 在测试壳加载客户端同 ABI SQLite；此层不是包内依赖或安装验证。
- `client/package.json`：只新增上述验证命令，不改版本、依赖、锁文件。
- `management/README.md`：同机与其他局域网电脑的连接地址、正常申请审批流程。

## 用户推送、合入与执行顺序

1. 用户自行审阅并提交当前分支的完整实现和 CI 文件。运行包 vendor 不入 Git；新的准备器、锁定下载清单、测试脚本和 workflow 必须随源码一起提交，不能只推 package/hook。
2. 用户自行推送并创建目标 main 的 PR、再合入 main。PR 验证和 main push 验证会跑新 `verify.yml`；仅推送功能分支本身不触发 main push 检查。新 workflow 首次合入默认分支 main 后，Actions 才提供其手动执行入口，此后可选择目标分支纯验证。它证明代码/离线契约/构建，**不会生成可下载的安装包**。手动触发的默认分支条件见 [GitHub 官方文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)。
3. 客户端正式发布须另行决定并准备稳定 `v1.8.4` tag：tag 包含最终代码和 workflow，运行 workflow 的 ref 与 tag 必须是同 SHA。main 在打 tag 后若有公告机器人等新提交，不要用新的 main SHA 去发布旧 tag；选择同一 tag/ref 新建运行，不能靠旧运行的 Re-run jobs 或弱化保护绕过。
4. 管理端 `management_ref` 选已合入 main 的对应版本源码，最好使用明确 SHA；独立发布版本必须是未占用版本。不要用已上传 R2 的相同管理端版本发布不同源码。本轮没有更改管理端源码版本或代替用户选择正式发布版本。
5. 手动发布具有真实外部副作用，仍需用户另行明确授权/操作及必要验收；包括 FFmpeg 分发许可、UI、实际模型与安装的既有待验收状态，不因新 CI 文件而自动完成。
6. 用户取得正规客户端与管理端包后，在本机先启动管理端、初始登录/改密并确认服务，再启动客户端填 `127.0.0.1:47821` 申请、审批和登录。开发启动端口分别5174/5173，授权服务端口47821；开发页面端口不能填到授权地址中。
