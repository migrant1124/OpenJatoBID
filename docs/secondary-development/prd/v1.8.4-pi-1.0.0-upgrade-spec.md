## 3. 必须保持的业务边界

### 3.1 Jato 控制层不替换

```text
既有业务页面 / 对话服务
        ↓ 既有 IPC 和业务协议
agentService：协调、排队、取消、提问
        ↓
piRuntimeService：工作区、运行、输出校验、修复、监视、自检
        ↓
piSessionFactory：内存状态、自定义 Provider、工具白名单、资源约束

        ↓
```

### 3.2 精简保护集合

不得重新注册以下现行导航入口或恢复它们的独占页面：

`bid-opportunity`、`resources`、`business-bid`、`image-knowledge-base`、`ai-evaluation`、`developer-prompt-lab`、`developer-parser-sandbox`、`developer-export-preview`。

## 5. 依赖升级与环境要求

### DEP01：精确版本

客户端两个直接依赖必须为：

```json
{
  "@earendil-works/pi-ai": "1.0.0",
  "@earendil-works/pi-coding-agent": "1.0.0"
}
```

解释：这里的 `1.0.0` 是第三方 Agent 内核版本，不是客户端版本。不加 `^`、`~`、`latest`，不使用 Git 分支依赖，不写成 1.0.1。

先核对 npm 仓库中精确版本、engines、dependencies、dist.integrity/发布元数据，再执行有范围的 npm 安装。仓库网络或包不可用属于阻断，不使用相似包、未知镜像或 Git 主分支代替。

### DEP02：传递依赖与锁文件

Pi 上游包内存在 npm-shrinkwrap。以 **1.0.0 实际发布包、其依赖约束及项目 lockfile** 共同确定安装树。[S13]

需要输出升级前后的依赖差异，检查所有运行相关 `@earendil-works/pi-*`、TypeBox、undici、WASM/原生模块的实际解析版本和位置。不得出现核心链路旧 `0.80.10` 与新 `1.0.0` 实例混用，或直接依赖虽为 1.0.0、实际 SDK 内部却解析到未经验证的另一版本。

同一 Pi 发布线的核心依赖按目标发布物固定核验；其他第三方包不因名称或同组织而一律改成 1.0.0。不能为追求“只有一个版本”滥用 overrides、删除上游 shrinkwrap 或强制 dedupe。确有冲突时，以真实接口/依赖证据确定最小修复，并记录。

禁止删除整个 lockfile 后重建、运行全量 npm update、`npm audit fix --force`、全仓换包、自动升级 TypeScript/Electron/Vite。允许目标升级引起的必要传递依赖变更；任何无关直接依赖漂移都应查明并消除，不掩盖 npm 生成的真实变更。

### DEP03：三种运行环境分别验证

| 环境 | 必须记录 |
| --- | --- |
| 开发/安装命令使用的 Node | `node --version`、npm 版本、CPU/平台 |
| Electron Main | 真实进程内 `process.versions.node`、`electron`、`modules`、架构 |
| Agent 启动的子进程 Node / 工具 | 按现有工具环境实际解析到的路径与版本，不能拿系统 Node 代替 |

上游 `>=22.19.0` 是 coding-agent 清单声明，不保证所有锁定传递依赖都只要求这一版本。[S13] 必须检查安装树中的 engines、原生 ABI、导入与实际工具运行。仅修改 `@types/node` 不会升级运行时。

当前 Electron/工具环境满足要求则不改。发现不能在现有环境运行时，不用忽略 engines、伪造版本或绕过原生模块检查；先记录是否需要最小环境升级。涉及 Electron 大版本、供应链或打包架构变化超出本规格，不自动实施。

## 6. Session 工厂与资源约束

### SDK01：真实 API 核对

对 `loadPiModules()`、`ModelRuntime.create/registerProvider/setRuntimeApiKey/getModel`、`SettingsManager.inMemory`、`DefaultResourceLoader`、`createAgentSession`、`SessionManager.inMemory`、所有使用的 ToolDefinition 工厂及 `defineTool`，逐一形成“当前调用 → 1.0.0 签名 → 是否需要修改 → 测试证据”表。

1. 继续从公开包入口动态 import ESM；不私自深层导入未导出的源码文件。
2. 不把项目整体改为 ESM，不安装独立 CLI，不新开 Server/RPC 架构。
3. 导入失败要保留可理解的错误；不捕获后假装初始化成功。存在失败 Promise 永久缓存等问题时，只做有测试支撑的最小处理。
4. 不必把变更日志中的每项 Breaking Change 都写进项目；只改真实命中的接口。
5. 真实 SDK 测试必须调用项目 Session 工厂，不能仅另写一个完全不同的官方示例证明能运行。

### SDK02：模型与会话状态

保持内存 CredentialStore、ModelsStore、SettingsManager、SessionManager，保持显式 workspace/agentDir，不读取用户全局 Pi 配置或通过上游默认值生成持久化状态。

保持 `provider=yibiao`、`model=default`、`api=openai-completions`、现有本地 Proxy Base URL/运行期令牌与 compat 配置的实际语义，不直接调用远端新 Provider，不自动登录任何新服务。

保持模式判定与思考策略：任务模式请求 off；对话模式沿用现有 requested_thinking_level / high 规则。**诊断中的实际思考级别读取 `session.thinkingLevel` 等真实公开状态**，不得简单复制 requested 值，也不为使诊断相同强制模型使用不支持的级别。

保持既有上下文/最大输出配置的计算与来源，允许测试验证新版压缩，不擅自把所有任务调成更大上下文、更高输出或更高思考档位。

### SDK03：必须显式冻结的新版行为

在受控的内存设置中增加：

```js
cacheWarming: 'off'
```

解释：关闭 Pi 的缓存保温功能，避免在运行过程中为保持模型缓存而额外发送请求。它不等于关闭正常请求、业务修复或上下文压缩，也不能据此承诺总 Token 必然减少。[S14]

保留 `enableInstallTelemetry: false`、`enableAnalytics: false`、`allowModelNetwork: false` 及不信任外部项目资源的语义。不要用“offline”总开关误伤合法的模型 Proxy 请求；`allowModelNetwork: false` 主要约束模型目录网络刷新，不能表述为整个 Agent 的网络防火墙。

测试应证明未触发新版缓存保温、外部模型目录刷新、新增登录/安装遥测或外部扩展发现。现有 Jato 业务统计保持原样，不因关闭 Pi 自身统计而被删除。

### SDK04：资源加载白名单

允许的资源为：Jato 当前注入的工作区/会话指令，以及经审查保留的 `jatobid-retry-error-normalizer` 内联扩展。Skill、文件式 prompt、主题、全局/祖先目录 AGENTS/CLAUDE、第三方扩展和新增内置扩展不自动加载。

保持 `noSkills`、`noPromptTemplates`、`noContextFiles`、`noThemes` 的关闭自动加载语义，且不增加 additionalSkillPaths/additionalExtensionPaths 等旁路。若关闭外部扩展发现需调整 `noExtensions`，必须用 1.0.0 实际行为证明 Jato 内联扩展仍加载，不能连同错误归一化一起禁用。

使用临时目录放置哨兵文件进行验证：假全局配置、祖先 AGENTS、`.pi/skills`、`.agents/skills` 和扩展中包含可识别标记；创建 Session 后这些标记不得进入 prompt/资源清单或引发执行。测试仅使用本轮临时目录，不修改用户真实 HOME 配置。

Pi CLI 会加载 Codemode/MCP 等内置扩展，而 SDK 需要显式接入；本轮不接入。[S11] 包中出现相关依赖、文件或导出不等于权限已启用，不为了“精简”直接删除这些 npm 运行依赖。

## 7. 工具、文件与用户提问

### TOOL01：工具集合严格不扩大

| 模式 | 允许的活动工具名称集合 |
| --- | --- |
| conversation | `read`、`find`、`ls` |

### TOOL02：对话只读约束

保留当前 lexical path 与 realpath 双重检查，验证 Windows 中文、空格、盘符、`..`、绝对路径、前缀相同的相邻目录，以及符号链接/junction 指向外部目录的场景。

正常读取工作区中的附件不受影响；工作区外数据不可被读取、列出或通过 find 遍历。应真正执行新版 read/find/ls 工具而不只调用辅助函数。Windows 特有场景需 Windows 证据，不能用 Linux 字符串模拟就声称通过。

### TOOL03：任务命令环境不另起方案

保持当前环境提供的 `shellPath`、命令前缀、UTF-8、工具路径及临时 HOME/TEMP 等设置。Windows 现有 bash 工具底层可使用项目选定 Shell，不因为上游新增 `powershell` 工具便新增工具、改名或要求员工安装 Git Bash/WSL/Python。

保持任务输入/输出相对路径限制、保留资源路径保护、当前工作区写入与输出校验。任务模式的通用 Shell 和原生文件工具**不应被声称为已有操作系统级强隔离**；发现既有弱点记录为既有风险，不借本轮承诺完成全沙箱。因升级引入的权限扩张必须修复或阻断。

### TOOL04：JSON 校验与提问

验证 TypeBox 实际 schema 可被 1.0.0 接受；工具参数和 details 必须符合新版 JSON 兼容值约定，不返回函数、循环对象或未经处理的 Error 实例。

保留预置 Schema 优先与 `json-validation` 严格校验，不删除 required、不放宽校验器来掩盖问题。无效 JSON/业务结构仍应失败并进入现有有界修复。

`ask-user` 沿用既有问答渠道，等待期间不误触发停滞中断；回答后只继续一次；取消/退出后问题失效且 Promise 结算，不在后续任务中出现旧问题。普通对话不新增该工具。

## 8. Proxy、事件、取消、重试与压缩

### RUN01：Proxy 契约不换线

对实际链路核验鉴权、loopback 地址与监听范围、流式/非流式响应、工具调用参数、tool_call_id、消息顺序、reasoning 字段、错误转换和 Token 统计。不得把测试通过建立在绕过现有 Proxy、队列或统计的直连上。

测试用可控本地假模型服务替代最远端供应商，但必须让真实 Pi SDK 经项目实际 Proxy/适配入口发出请求；证据标明“真实 SDK + 真实项目 Proxy + 本地模拟供应商”，不是“真实外部模型通过”。

### RUN02：最终完成边界

1. 继续等待公开 `session.prompt()` 返回及既有业务输出校验，不收到一个 `agent_end` 就宣布任务结束。
2. 上游说明 `agent_end` 后仍可能自动恢复或继续；需要监听最终稳定边界时使用 `agent_settled`，并核对当前项目调用处。[S11]
3. 完整消息以 `message_end` 对应完成态为依据，增量事件不能被当作已完成正文。
4. 一次业务任务只能有一个最终成功或失败，不得重复写 Store、重复完成通知或让晚到事件污染下一任务。
5. 未通过输出校验不能只因最后回复说“完成”而成功。

### RUN03：取消、队列与资源释放

保留 agentService 协调队列，不改并发模型，不以新 SDK 提供 steer/followUp 就改造现有排队逻辑。

覆盖排队中取消、模型请求中取消、工具执行中取消、重试等待中取消、压缩中取消、等待用户回答时取消和应用退出。取消必须传播到请求/工具；清理前等待真实工作停止，避免旧工具写入已清空、已被下一任务复用的目录。

finally 中事件订阅、会话、计时器、挂起问题与临时资源按新版生命周期完成释放，错误清理不能覆盖原始失败。连续执行与失败恢复测试应证明下一任务可用。若 ModelRuntime 或其他新创建资源有独立公开释放接口，只对本轮拥有的实例正确释放，不销毁共享 Proxy。

### RUN04：重试分层

分别记录并核对：供应商/HTTP 重试、Pi agent 重试、Jato 输出校验修复。保持当前业务 max_retries、超时及队列语义；对旧版依赖默认值先实测/核对，不凭猜测重新指定更大的重试预算。

`provider.maxRetries=0` 等现有设置应保持其实际语义；新版新增默认值如果影响请求次数，应显式冻结到基线意图。短暂不可用可按现有预算恢复；明确认证错误、用户取消不能无限重试。

对自定义 `message_end` 错误归一化扩展，验证其修改是否进入 1.0.0 真正的重试判定。需要时按公开接口适配，避免重复前缀或同一错误被多个适配层反复包装。不能为了省事完全关闭原有必要重试。

### RUN05：上下文压缩与会话历史

保持 compaction 开启与既有业务历史来源，不新增永久会话库。新版 SessionManager 是最终模型上下文的权威来源；检索项目真实调用是否存在直接写 `session.agent.state.messages`、旧结束钩子或旧事件形状，命中才迁移。[S11]

长资料测试用受控模型模拟超过阈值，确认工具输出、最新用户需求、工作区关键事实在压缩后的后续请求中仍可用；不能靠关闭压缩、删除材料或截断到测试通过来规避。

现有对话历史由应用层重建时，保留其既有拼装/存储行为。不要仅因上游支持持久化就另造恢复系统。压缩失败必须可诊断，不能以空摘要假装成功。

## 9. 自检、监视器、合规与操作留痕

### DIAG01：实际运行版本

沿用既有自检/诊断/监视器，不新增一级入口或版本切换 UI。记录：应用版本、Pi coding-agent 实际 VERSION、pi-ai 实际安装版本（以可靠元数据为准）、Electron/Node/平台、模式、活动工具、资源摘要、缓存保温状态、请求/有效思考级别，以及失败阶段。

工具没有实际运行、Schema 未通过、活动工具意外增加或版本不是目标值时，自检不能显示正常。SDK 资源显示格式变化可以做最小归一化，但不能简单删除扩展检查来通过。

### SAFE01：数据与人工审核

不得读取生产客户招标文件用于自动回归，不把原文、员工身份、API Key、授权 JSON、私钥或真实路径写入可提交证据。使用合成、匿名资料；测试样本与新增文案不得夹带无关竞争对手名称或敏感客户信息。

正式投标正文仍沿用既有人工审核与导出后自审方式，不为本次依赖升级增加敏感词/竞品扫描模块、生成前确认弹窗，也不移除已有审核、来源核对和操作留痕。不得修改供应商安全限制。

本轮新日志只记必要元数据与脱敏错误摘要；现有本地任务存档保持，不新增向外发送正文/Prompt 的渠道。真实外部模型测试仅使用合成内容和已有明确允许的凭据配置，不自动提取个人配置、不新申请账号、不扩大权限、不进行批量付费回归。

## 11. Codex 分步实施流程

以下步骤在同一轮指令中连续执行。每步记录输入、实际结果、证据位置；无实质阻断不重复等待计划确认。

### 步骤 1：只读基线核验

**输入：** 当前本地仓库、本规格、精简规格、`AGENTS.md`、`开发说明.md`、适用的子目录 AGENTS/仓库工作流规范及现有计划。

**动作：** 读取当前分支、HEAD、status、remote；确认分支为 `v1.8.4-架构优化`、应用版本 1.8.4、精简集合仍有效，识别所有未提交/未跟踪改动。核对现有测试和构建脚本，不沿用历史“无测试”的描述。

**输出：** 基线记录、保留/禁止变更集合、现有环境/依赖/测试基线、风险清单。

**约束：** 只使用只读 Git 命令，不 fetch/pull，不回退到审查 SHA；源目录以实际仓库为准，不因旧本地路径大小写或位置不同操作错误仓库。

### 步骤 2：调用链与 1.0.0 契约审计

**输入：** 现有 Pi/Agent/对话调用代码、目标发布包与 v1.0.0 官方 API。

**动作：** 跟踪真实模块导入、Session、工具、Proxy、事件、重试、取消、压缩和自检；形成兼容矩阵，确认每个修改的原因与作用范围。

**输出：** 追加到 `tasks/plan.md` 的本轮计划及 `tasks/todo.md` 的 `PI184-*` 任务，不创建平行权威 todo。

**约束：** 不混入产品功能；重大额外环境迁移记录为范围外阻断。范围内计划完成后直接执行，不停在“请确认”。

### 步骤 3：受控依赖安装

**输入：** 精确目标 1.0.0、原 package/lockfile、环境和发布元数据。

**动作：** 使用 npm 精确升级两个包，审查必要传递变化；验证 npm ci 可重现、目标版本实际解析正确，执行依赖审计。

**输出：** 新锁文件、前后依赖差异、engines/ABI 核对、安装与 audit 记录。

**约束：** 应用版本不变，不删锁文件，不全量升级，不忽略引擎，不误用 npm version。

### 步骤 4：最小 SDK 适配

**输入：** 契约矩阵与实际安装的 1.0.0。

**动作：** 修复真实不兼容；显式关闭 cacheWarming；冻结资源/工具/Provider/内存状态边界；更新真实快照；保持业务返回协议。

**输出：** 必要源码差异及对应单元/集成测试。

**约束：** 不换 Agent、不扩权、不重构 UI/数据库，不用静默降级或假数据让自检通过。

**输入：** 真实 SDK、项目 Session/Proxy、隔离临时目录、合成资料和本地模拟供应商。

**动作：** 正常任务、对话附件、工具只读/参数校验、错误恢复、取消、问答、长上下文、资源加载与额外网络检查；修复本轮引入的问题。

**输出：** 审查发现、修复证据、剩余问题及范围声明。

## 16. 主要风险与处理原则

| 风险 | 处理原则 |
| --- | --- |
| 上游接口保留，但事件最终结束语义有变化 | 用真实恢复/取消序列验证，不只依据函数名称 |
| 新默认 cacheWarming 产生额外请求 | 明确设 off，并验证实际调用/计时器路径 |
| npm-shrinkwrap 与传递依赖让实际树不同于预期 | 核查发布物、lockfile、npm ls 与运行时模块解析 |
| CJS 源文件不受前端 tsc 完整覆盖 | 必须真实 import/创建 Session/工具执行 |
| 对话工具同名覆盖失效 | 实际执行越界负向用例，验证调用的是受控实现 |
| 同一工作区复用时取消未结算 | 工具/请求退出后再清理，连续任务检查旧结果污染 |
| Windows Node/原生/WASM/asar 差异 | 分开验证系统 Node、Electron、子进程与包内环境 |
| 缺真实模型或实体 Windows | 继续能做的工作，但缺项明确阻断完整验收 |
| 旧文档与新代码名称不一致 | 不恢复 OpenCode、不重命名桥接；记录冲突并保持当前有效调用 |
| 为升级顺手恢复/增加功能 | diff 审查和精简负向用例作为范围门禁 |
