# OpenJatoBID v1.4.5 投标文件质量增强实施规格

## 0. 本规格的用途

本文件用于直接指导 Codex 在 `migrant1124/OpenJatoBID` 仓库中，以最新 `main` 为实施基线，在 `codex/v1.4.5-bidq` 分支完成 `v1.4.5` 的投标文件质量增强。原 `agent/fix-safety` 中的安全保护能力已经合并进入 `main`，本轮不得丢弃、绕过或重复实现这些能力。

本规格关注的不是程序调用顺序本身，而是将专业投标团队的编制方法落入产品工作流，使系统生成的目录、正文、表格和图片具备更高的评分命中率、技术可执行性、信息密度、证据充分性和评审可读性。

本规格是实施规范，不是讨论稿。Codex 必须先核实当前仓库状态；已满足的要求以测试和可复现证据确认为主，不得为了制造 Diff 重写现有实现。尚未满足的要求必须实施，并提供自动化测试、人工验收步骤和风险说明。

本规格的核心目标是：

```text
招标要求原子化
→ 评分响应策略
→ 增值锚点识别
→ 评分/否决/隐性附件三重反查
→ 高质量目录与深度写作标记
→ 章节写作合同
→ 层级化正文生成与统稿
→ 表格和图片提前策划、最终生成
→ 多维质量审核
```

本规格不授权 Codex 推送、合并、部署、打 Tag、创建 Release 或提升任何更新清单。所有远程写入必须获得用户明确授权。

## 1. 本次修订的最高优先级决策

以下决策覆盖此前讨论、旧规格或代码注释中与之冲突的内容。

### 1.1 基线分支与实施分支

本轮固定使用：

```text
BASE_BRANCH           = main
IMPLEMENTATION_BRANCH = codex/v1.4.5-bidq
```

原 `agent/fix-safety` 分支中的目录和正文安全保护能力已经合并进入 `main`。Codex 必须先同步并核实最新 `main`，确认 `bootstrap.cjs`、guarded task service、目录 Guard、正文 Guard 及其回归测试均存在，再创建或切换到 `codex/v1.4.5-bidq` 开始实施。

创建方式：

```text
main
→ codex/v1.4.5-bidq
```

若 `codex/v1.4.5-bidq` 已存在，Codex 不得删除、重建或强制覆盖；必须先核实其基线、提交历史、工作区状态和与最新 `main` 的关系，再继续工作。

若工作区已有未提交修改，Codex 必须先报告，不得覆盖、清理或擅自暂存用户修改。

### 1.2 安全保护层属于受保护基线

下列能力必须保留：

- 目录候选先暂存、校验通过后原子提交。
- 目录 ID 确定性编号与重复/空值校验。
- `original-only` 与 `ai-complement` 的模式隔离。
- 最终目录语义审核与有界 Agent 修复。
- 正文整体重生成安全快照和异常恢复。
- 正文编排失败阻止无约束正文落库。
- 原方案实质段未分配检查。
- 有正文叶子节点下补目录的保护。
- Electron 启动时通过 `bootstrap.cjs` 加载 guarded task service。

以下文件属于 **受保护路径 / PROTECTED PATH**，只能做局部、可审查、具备回归测试的语义修改：

```text
client/electron/bootstrap.cjs
client/electron/services/guardedTaskService.cjs
client/electron/services/outlineGenerationGuard.cjs
client/electron/services/contentGenerationGuard.cjs
client/electron/services/technicalPlanGuardUtils.cjs
client/electron/services/technicalPlanTaskGuards.test.cjs
client/electron/services/technicalPlanTaskGuards.recovery.test.cjs
```

不得绕过保护层直接恢复原任务入口，不得把保护层功能复制到另一套并行实现。

### 1.3 本轮质量目标

`v1.4.5` 必须把系统从：

```text
合规目录生成器
+ 独立小节正文生成器
+ 事实纠错器
+ 后置配图器
```

提升为：

```text
评分响应策划器
+ 增值锚点发现器
+ 深度目录与章节写作合同生成器
+ 章节级投标正文编制器
+ 创意方案视觉策划与多图生成器
+ 评委视角质量审核器
```

### 1.4 已锁定的产品规则

本轮必须实现以下规则：

1. 目录生成增加“增值锚点识别”。
2. 增值锚点必须比较招标明确要求与行业高标准工程或策划实践，识别能够展示综合实力、提升技术文件质量的留白区。
3. 增值锚点不得无条件变成目录；必须经过相关性、可实施性、内容承载力、证据和重复性 Gate。
4. 每个原子评分点必须反查并映射至目录节点。
5. 每条否决或潜在废标项必须进入高风险台账，并形成明确应对路径。
6. 附录、脚注、表格下说明及交叉引用中的隐性格式/附件要求必须反查并路由。
7. AI 必须识别需要深度写作的二级目录，并默认勾选“深度写作”。
8. 深度写作二级目录必须至少形成一条完整的 `二级→三级→四级→五级` 路径。
9. 关键四级节点必须继续拆解到五级；不得要求所有四级节点机械增加无内容的五级子节点。
10. 普通目录分支最高四级；只有深度写作二级目录的子树允许五级。
11. 增加“AI 深化本节目录”功能，对一个选定二级目录进行增量深化，不全量重生成目录。
12. 局部深化默认保留现有二级标题及其全部现有子标题，只允许补充、完善和重新分配质量元数据。
13. 深度写作和增值锚点章节必须使用专门的正文写作合同和提示词。
14. AI 图片必须支持广告宣传、活动策划、传播方案、空间和物料设计等创意场景。
15. 取消“每个小节只允许一张图”的规则。
16. 具体配图数量由 AI 根据章节类型、信息增益和全文预算决定，但不得突破硬性总量和重复性规则。
17. 图片计划必须支持段落级插入锚点，避免多张图堆积在小节开头或结尾。
18. 默认图片配置改为：HTML 开启、最多 30 张；AI 模型可用时开启、最多 20 张；Mermaid 默认关闭、最多 5 张；HTML 类型默认全部可选。
19. 上述数量是硬上限，不是必须填满的目标。
20. 现有用户明确保存的自定义图片数量不得在迁移时被强制覆盖。
21. 普通正文节点的编辑下拉框只提供 `AI编写` 和 `人工填写`，保存后对应显示同名标签。
22. `AI编写` 与 `人工填写` 必须互斥，左侧目录树和右侧目录项详情必须一致；旧标签 `AI正文` 必须全部移除。
23. 固定表格、固定承诺函、证明材料、明确无内容响应和目录容器只显示专用标签，不附加 `AI编写` 或 `人工填写`。
24. 普通正文填写方式继续由现有 `manual_input_required + freeform-markdown` 语义派生，不新增重复持久化字段。

### 1.5 本轮不以“总字数”作为主要质量指标

最低字数功能继续保留，但必须从单纯的总字数补足，升级为评分价值和内容缺口驱动：

```text
章节目标篇幅
≈ 评分权重
× 技术复杂度
× 风险等级
× 证据需求
× 差异化价值
```

不得仅按“最短章节优先”无差别扩写，不得为了达到字数重复已有内容。

### 1.6 本轮不实施的事项

以下内容不属于 `v1.4.5`：

- 重写整个 `contentGenerationTask.cjs` 或 `outlineGenerationTask.cjs`。
- 建立通用跨业务工作流引擎。
- 建立完整品牌资产管理中心。
- 自动生成或伪造客户 Logo、公司资质、人员证书和真实案例。
- 让模型自由修改固定目录、固定承诺函或人工填写节点。
- 将 AI 图片数量上限解释为生成目标。
- 允许五级目录出现在普通目录分支。
- 批量同时深化多个二级目录；`v1.4.5` 第一版只支持单目标局部深化。
- 因质量优化而删除或绕过现有安全保护层。
- 为普通正文填写方式新增与 `manual_input_required` 重复的第二持久化字段。

## 2. 规范性用语

- **必须 / MUST**：不可省略。
- **不得 / MUST NOT**：明确禁止。
- **应该 / SHOULD**：除非存在可验证的技术阻碍，否则实施。
- **可以 / MAY**：可选。
- **验证项 / VERIFY-ONLY**：当前实现可能已经满足，先测试，缺失时才修改。
- **受保护路径 / PROTECTED PATH**：只能局部语义修改，禁止整体覆盖。
- **规范产物 / CANONICAL ARTIFACT**：后续阶段必须消费的权威数据，派生结果不得反向篡改其语义。
- **硬上限 / HARD LIMIT**：程序必须确定性限制，模型不得突破。
- **软密度 / SOFT DENSITY**：用于提示和排序，不要求填满，也不作为单独失败条件。
- **质量门禁 / QUALITY GATE**：未通过时不得将任务标记为普通成功。
- **人工确认 / MANUAL CONFIRMATION**：涉及真实能力、实际承诺、品牌资产或无法从资料证实的信息时，必须显式提示用户确认。

# 第二部分：招标要求原子化与增值锚点

## 5. 招标要求原子化

### 5.1 原子化目标

现有评分大类必须继续保留以兼容 `source_requirement_id`，但目录质量和正文质量审核必须下钻到原子评分点。

示例：

```text
R1      实施方案
R1.P1   实施阶段划分
R1.P2   实施进度与关键节点
R1.P3   项目组织和职责
R1.P4   质量控制措施
R1.P5   风险与应急保障
```

### 5.2 原子评分点提取规则

必须识别：

- 评分项名称。
- 分值或权重。
- 评分标准中的每个独立得分动作。
- “优、良、一般”等分档条件。
- 扣分条件。
- 明确要求的表格、图片、证明材料或承诺。
- 来源章节、页码、表格或脚注位置。

不得：

- 把一整段评分标准压缩成一个模糊 `detail_point`。
- 把通用评分规则误当作独立技术内容。
- 因为没有明确分值就忽略实质性技术要求。
- 将商务报价、资格项混入技术方案正文映射；应根据响应路由进入其他检查项。

### 5.3 长文档处理

招标要求原子化必须支持按上下文预算分段、滚动合并和补漏。分段输出必须保留来源引用，最终合并不得丢失已识别原子项。

### 5.4 评分响应策略

每个原子评分点必须生成：

```text
评委想看到什么
基础响应必须包含什么
高分响应需要额外体现什么
使用什么事实、证据、表格或图片证明
最适合由哪个目录节点承担
```

该策略必须进入 `AtomicScoringPoint.high_score_conditions` 和后续 `SectionWritingContract`。

## 6. 增值锚点识别

### 6.1 定义

增值锚点是招标明确要求与高标准工程、服务或策划实践之间的合理留白区。它用于体现方案完整性、风险意识、综合实力和可执行性，不得用于虚构企业能力。

### 6.2 典型示例

```text
招标方仅要求“售后服务”
→ 候选增值锚点：重大售后事件分级响应与升级机制
→ 候选增值锚点：售后服务应急预案体系
→ 候选增值锚点：服务质量监测、回访和持续改进闭环
```

```text
招标方仅要求“实施进度”
→ 候选增值锚点：关键路径偏差监测与纠偏机制
→ 候选增值锚点：极端边界条件下的进度韧性保障
→ 候选增值锚点：关键节点延误应急赶工方案
```

“极端边界条件下的应急响应流程”若与进度职责边界不一致，应收敛为进度韧性或赶工机制；通用事故应急应路由到风险与应急章节。

### 6.3 识别输入

增值锚点识别必须综合：

```text
招标明确要求
+ 原子评分点和高分条件
+ 否决/高风险条款
+ 用户原方案中的既有能力
+ 所选知识库中的行业实践
+ 当前目录已覆盖内容
```

不得只凭模型常识批量生成通用目录。

### 6.4 来源优先级

```text
招标文件明确内容
> 用户原方案
> 用户知识库
> 内置行业实践模板
> 模型一般经验
```

由“模型一般经验”单独支持的锚点必须标记为 `industry-template` 或 `needs-confirmation`，不能生成具体人员、型号、客户案例、证书、数量或承诺时限。

### 6.5 目录准入 Gate

一个候选锚点只有同时满足以下条件，才能 `route = directory`：

1. 与项目范围和评分主题直接相关。
2. 能提高评分命中、方案完整性或履约风险控制能力。
3. 能写出具体机制、流程、参数、责任和产物。
4. 有足够信息支撑一个独立小节。
5. 不依赖无法证实的企业资质、案例、人员或设备。
6. 不与现有目录职责重复。
7. 不破坏招标固定目录和响应模式。

不满足目录准入条件时，必须降级路由为：

- `writing`：现有章节写作要点。
- `table`：结构化表格建议。
- `illustration`：图片建议。
- `risk`：风险台账。
- `manual-review`：待人工确认。

### 6.6 增值锚点类别

必须至少支持：

| 类别 | 典型内容 |
|---|---|
| 韧性与应急 | 极端场景、重大故障、备用资源、业务连续性 |
| 质量提升 | 质量门禁、抽检复核、过程审计、缺陷闭环 |
| 进度保障 | 关键路径、偏差阈值、赶工方案、里程碑复核 |
| 可验收性 | 验收指标、交付清单、质量记录、确认机制 |
| 服务能力 | SLA、升级通道、重大事件响应、回访改进 |
| 风险治理 | 风险分级、触发条件、责任升级、关闭验证 |
| 数据闭环 | 指标采集、分析、优化和复盘 |
| 协同治理 | 甲乙方职责、沟通、决策升级、变更管理 |
| 创意增值 | 用户洞察、创意策略、传播矩阵、效果测量 |
| 可视化表达 | 架构、流程、进度、职责、效果设计图 |

### 6.7 去重与数量控制

增值锚点生成后必须执行：

- 标题语义去重。
- 与现有目录职责去重。
- 同一评分点下的锚点合并。
- 不具备正文承载力的锚点降级。
- 同一二级目录下新增目录锚点原则上不超过 5 个；超出时必须合并或路由为写作要点。

## 7. 三重反查

### 7.1 评分反查

每个 `AtomicScoringPoint` 必须：

- 有且仅有一个主要负责节点 `primary_node_id`。
- 可以有辅助节点，但不得由多个章节重复承担完整正文。
- 映射至二级及以下节点。
- 高分条件必须进入目录描述或章节写作合同。
- 需要表格、图片或证明材料时，必须形成对应 Brief。

质量门禁：

```text
scoring_points.total
=
scoring_points.mapped + scoring_points.explicit_not_applicable
```

任何 `unmapped` 原子评分点都必须使目录普通成功失败。

### 7.2 否决反查

每条否决或潜在废标项必须进入 `RejectionRiskItem`，并选择正确路由。

示例：

| 否决项 | 路由 |
|---|---|
| 技术方案缺少强制售后承诺 | fixed-form / outline |
| 未提交证明材料 | evidence |
| 未签字盖章 | submission / manual-review |
| 文件命名不符合要求 | export / submission |
| 固定表格缺失 | fixed-form |
| 技术参数重大偏离 | content / evidence / manual-review |

不得把签章、文件名、上传格式等行政检查项强行生成技术正文目录。

质量门禁：

```text
rejection_risks.total
=
covered + not_applicable + needs_confirmation
```

`needs_confirmation` 必须在 UI 高风险区显示，不得静默通过。

### 7.3 隐性附件反查

必须扫描：

- 附录和附件目录。
- 脚注。
- 表格下方说明。
- “详见附件”交叉引用。
- 固定模板。
- 文件命名、页数、份数、上传格式。
- 外部附件或证明材料要求。
- “如适用”“必须提供”“按附件格式填写”等限定语。

每项隐藏要求必须路由至：

```text
outline
content
fixed-form
evidence
export
submission
manual-review
```

不得只记录日志而不形成后续处理状态。

### 7.4 高风险区 UI

目录页或技术方案工作流中必须增加可折叠“高风险与隐藏要求”区域，至少显示：

- 否决风险总数。
- 已覆盖、待确认、未处理数量。
- 隐性附件要求总数和路由。
- 点击项目后定位对应目录节点或处理说明。

该区域不得阻塞用户浏览目录，但存在 `unhandled` 或 `potential-rejection + needs-confirmation` 时必须有明显风险标识。

# 第三部分：目录质量增强与深度写作

## 8. 目录生成总流程

目录生成流程调整为：

```text
1. 读取固定格式和来源骨架
2. 提取评分大类和原子评分点
3. 提取原方案目录（已有方案扩写）
4. 生成增值锚点候选并路由
5. 形成评分响应矩阵
6. 生成普通目录骨架
7. AI 判断二级目录写作类型和深度写作建议
8. 对深度二级目录生成三级、四级、五级结构
9. 执行评分反查
10. 执行否决反查
11. 执行隐性附件反查
12. 执行程序结构校验
13. 执行目录语义和重复性审核
14. 必要时执行一次有界 Agent 修复
15. 通过安全保护层原子提交
```

### 8.1 一级目录规则保持不变

- 招标文件明确目录时，一级目录严格来自招标文件。
- 招标文件未明确目录时，一级目录仍来自用户选定的知识库文档标题结构。
- 增值锚点和评分点不得新增、改名或移动固定一级目录。
- 增值锚点只能在允许的二级及以下位置承载。

### 8.2 目录标题要求

目录标题必须：

- 专业、简洁、可定位。
- 表达具体职责或方案模块。
- 避免直接复制冗长评分标准。
- 避免“相关措施”“其他内容”“综合保障”等模糊标题。
- 避免同义重复。
- 五级标题应是可直接执行的写作任务，不是长句正文。

---

## 9. 深度写作识别

### 9.1 适用节点

“深度写作”只允许设置在二级目录节点。子节点继承最近的二级祖先写作类型。

### 9.2 AI 推荐条件

符合任一高价值条件时，AI 应推荐并默认勾选：

- 对应高分评分项或多个原子评分点。
- 属于总体架构、实施方案、创意策划、质量控制、风险应急、服务保障等复杂主题。
- 需要明确流程、组件交互、参数、SLA、责任、验收或交付物。
- 存在一个或多个已接受的增值锚点。
- 需要多张图或多个高价值表格。
- 原方案或知识库有较丰富素材。
- 直接关系否决、高风险或履约可执行性。

### 9.3 禁止节点

以下节点不得设置深度写作：

- `manual_input_required = true`。
- `fixed-markdown-table`。
- `locked-commitment`。
- `evidence-markdown`。
- `explicit-none`。
- `container` 且不允许 AI 子目录。
- `allow_ai_children = false`。

### 9.4 新增目录字段

`OutlineItem` 必须新增并持久化：

```ts
deep_writing?: boolean;
deep_writing_recommended?: boolean;
deep_writing_reason?: string;
deep_writing_source?: 'ai' | 'user' | 'default';
writing_profile?: 'standard' | 'deep' | 'creative-proposal';
value_anchor_ids?: string[];
mapped_scoring_point_ids?: string[];
```

规则：

- `deep_writing` 只在二级节点具有权威意义。
- `creative-proposal` 自动视为深度写作，但 UI 应显示其创意策划属性。
- 用户取消 AI 推荐后，`deep_writing_recommended` 保留，`deep_writing = false`。
- 用户手动勾选后，`deep_writing_source = user`。

## 10. 五级目录语义和结构

### 10.1 层级职责

```text
二级：方案主题或核心职责
三级：核心模块或应用场景
四级：微观工序、执行动作或具体组件
五级：参数基线、SLA、边界条件、工作产物或闭环标准
```

### 10.2 三至五级生成规则

#### 三级：核心模块/场景

必须基于：

- 招标要求。
- 原子评分点。
- 已接受增值锚点。
- 原方案和知识库中与该二级目录相关的能力。

#### 四级：微观工序/组件

- 实施类必须拆成原子化操作。
- 流程类必须拆成可执行节点和判断。
- 架构类必须拆成组件职责和交互。
- 服务类必须拆成受理、判断、执行、升级、关闭等动作。
- 策划类必须拆成洞察、创意、内容、媒介、执行、评估等单元。

#### 五级：参数基线/SLA/边界/产物

五级必须至少承载一种可验证细节：

- 参数与指标。
- 时限和 SLA。
- 触发阈值。
- 正常、异常或极端边界。
- 输入和输出产物。
- 检查、验收和关闭条件。
- 流程图、逻辑图、架构图或方案设计图的明确任务。

### 10.3 “必须达到五级”的精确定义

每个 `deep_writing = true` 的二级目录必须：

- 子树最大深度等于 5。
- 至少存在一条完整 `L2→L3→L4→L5` 路径。
- 所有被判定为关键的四级节点必须有至少一个五级子节点。
- 非关键四级节点若已经是完整、可执行的任务，可以保持叶子，不得机械生成无内容五级节点。

### 10.4 规模控制

建议目标：

```text
每个深度二级目录：
三级目录 2–6 个
每个三级目录下四级目录 2–5 个
关键四级目录下五级目录 1–4 个
整个二级子树叶子节点原则上不超过 30 个
```

程序质量审核必须识别明显目录爆炸，并要求合并同类项。30 不是绝对拒绝阈值；若超过，模型审核必须给出“为什么无法合并”的明确理由，否则不得通过。

### 10.5 条件深度校验

目录安全校验必须从全局“最多四级”改为：

```text
普通二级子树：最大深度 <= 4
深度写作二级子树：最大深度 = 5
任何非深度二级子树：禁止出现五级节点
整个目录：禁止出现六级及以上节点
```

### 10.6 目录页显示深度

导出目录页默认显示到四级；用户可以选择显示到五级。正文中五级标题始终正常渲染。

该规则只影响目录页显示，不得删除五级正文结构。

## 11. “AI 深化本节目录”功能

### 11.1 产品入口

在目录编辑页选择一个二级目录时，显示：

```text
[ ] 深度写作
AI 推荐原因：……
[ AI 深化本节 ]
```

若 AI 已推荐，复选框默认勾选。

### 11.2 第一版作用范围

`v1.4.5` 仅支持一次选择一个二级目录，不支持多选批量深化。

### 11.3 默认行为

“AI 深化本节”必须是增量深化，不是局部全量重写：

- 保持选定二级目录 ID、标题和顺序。
- 保持该二级目录下所有现有标题。
- 保持固定、锁定、人工和受控响应节点。
- 不修改其他二级目录及其子树。
- 不删除现有节点。
- 可以完善现有节点描述。
- 可以新增三级、四级和五级目录。
- 可以补充评分点映射、增值锚点和写作类型元数据。
- 深度写作开启时必须达到五级。
- 输出前必须执行该子树的评分、风险和隐性要求反查。

### 11.4 增值选项

局部深化对话框应提供：

```text
[✓] 识别并增加增值锚点
```

在 `original-only` 模式中：

- 默认只能使用原方案和来源骨架已有标题。
- 增值锚点只作为建议展示，不自动新增来源外标题。
- 用户明确选择“允许 AI 增值深化”后，才可以按评分点和项目语境新增标题。
- 该选择必须记录到任务参数和日志，不能隐式突破 `original-only`。

### 11.5 局部 Patch 规范

AI 不得返回完整目录，必须返回局部 Patch：

```json
{
  "schema_version": 1,
  "target_node_id": "3.2",
  "deep_writing": true,
  "updates": [
    {
      "node_id": "3.2.1",
      "description": "完善后的职责说明"
    }
  ],
  "additions": [
    {
      "parent_id": "3.2.1",
      "title": "重大服务事件分级响应",
      "description": "明确事件分级、启动条件、响应时限和升级机制",
      "children": [
        {
          "title": "事件受理、研判与分级",
          "description": "拆解事件识别和级别判定动作",
          "children": [
            {
              "title": "分级阈值、响应时限与记录产物",
              "description": "明确判定基线、SLA和闭环记录"
            }
          ]
        }
      ]
    }
  ],
  "scoring_point_mappings": [],
  "value_anchor_ids": []
}
```

### 11.6 Patch 校验

程序必须确定性检查：

- `target_node_id` 是真实二级节点。
- `updates.node_id` 全部位于目标子树内。
- `additions.parent_id` 全部位于目标子树内。
- 不删除、不移动、不改名现有标题。
- 不修改锁定字段。
- 新增节点层级不超过五级。
- 五级只出现在深度写作子树。
- 新增标题同级不重复。
- 评分点 ID 和增值锚点 ID 均有效。
- 目标子树最终通过条件深度和评分覆盖审核。

### 11.7 差异确认

应用 Patch 前必须展示差异：

- 新增节点。
- 完善的描述。
- 新增评分点映射。
- 新增增值锚点。
- 深度写作状态变化。
- 对已有正文、计划和图片的影响范围。

用户确认后才提交。

### 11.8 已有正文关联处理

- 正文尚未生成：直接提交局部深化结果。
- 全局事实已生成、正文未生成：保留事实；若新增节点需要新的事实组，标记 Step04 需要增量补充。
- 正文已生成：仅失效目标二级子树相关的正文计划、正文和图片。
- 其他二级目录正文不得清空或重新生成。
- 旧叶子变成父节点时，旧正文不得直接删除；必须作为待重新分配的来源素材，映射至新增叶子后再清理父节点正文。
- 局部深化失败时必须保留原目录、原正文和原图片。

### 11.9 后台任务

建议新增独立任务类型：

```text
outline-deepening
```

建议状态字段：

```text
outlineDeepeningTask
```

不得把局部深化伪装成全量目录生成后再尝试恢复其他节点。

## 12. 目录质量审核

最终目录审核必须同时检查：

- 固定目录和来源约束。
- 原子评分点覆盖。
- 评分高分条件是否进入目录说明或写作合同。
- 否决风险和隐性要求路由。
- 增值锚点相关性与可实施性。
- 章节职责边界。
- 同义重复。
- 目录粒度与评分价值匹配。
- 普通/深度子树层级规则。
- 深度子树是否真正包含参数、SLA、边界或产物任务。
- 是否存在为了达到五级而制造的空壳标题。

审核失败时最多执行一次 Agent 修复。修复后必须重新运行全部程序校验和语义审核。

# 第四部分：正文写作合同与质量提升提示词

## 13. 正文计划升级至版本 5

### 13.1 兼容与迁移

- 将 `CONTENT_PLAN_VERSION` 从 4 升级到 5。
- 版本 4 计划只读兼容，不得直接作为版本 5 权威计划复用。
- 版本 4 计划存在时，可以提取知识条目、事实和原方案来源作为候选输入，但必须重新生成版本 5 写作合同。
- 目录、评分矩阵、全局事实或知识库版本变化时，版本 5 计划必须失效。

### 13.2 输入指纹

每个计划必须保存：

```ts
interface ContentPlanFingerprint {
  outline_node_hash: string;
  parent_outline_hash: string;
  scoring_matrix_revision: string;
  global_facts_revision: string;
  knowledge_document_revisions: string[];
  original_plan_hash?: string;
  prompt_version: string;
  writing_profile: string;
}
```

任一关键指纹变化时不得静默复用旧计划。

### 13.3 章节级策划

同一二级目录下的叶子小节生成前，必须先生成二级章节任务书，明确：

- 本章目标。
- 对应评分点。
- 核心结论。
- 各小节职责。
- 章节间边界。
- 表格和图片布局。
- 目标篇幅分配。
- 证据和用户确认项。

不同二级章节可以并行策划；同一二级章节的小节必须共享该任务书。

## 14. 写作类型

### 14.1 `standard`

适用于一般说明、普通响应和低复杂度章节。

### 14.2 `deep`

适用于高分、复杂、需要执行细节、SLA、参数、边界和产物的章节。

### 14.3 `creative-proposal`

适用于广告宣传、品牌传播、活动策划、展陈、内容运营和创意方案章节。

`creative-proposal` 必须同时体现：

- 客户特点。
- 项目目标。
- 目标受众。
- 核心主题或传播主张。
- 创意策略。
- 执行载体。
- 传播节奏。
- 现场或空间设计。
- 效果评估。
- 对应的创意图片 Brief。

## 16. 正文生成方式

### 16.1 层级化生成

正文生成顺序应该为：

```text
二级章节任务书
→ 章内小节写作合同
→ 叶子小节生成
→ 二级章节统稿
→ 全文统稿和质量审核
```

不得只依赖所有叶子小节彼此独立并发生成。

### 16.2 并发规则

- 不同二级章节可以并发。
- 同一二级章节中的叶子小节可以在共享任务书后有限并发。
- 二级章节统稿必须在该章所有叶子小节完成后执行。
- 全文统稿必须在所有章节完成后执行。

### 16.3 章节统稿边界

统稿可以：

- 删除重复表达。
- 统一术语。
- 增加必要过渡。
- 修正章节职责越界。
- 补齐写作合同中的缺口。

统稿不得：

- 修改目录结构。
- 删除已确认的招标响应和原方案实质内容。
- 新增无来源的具体承诺。
- 覆盖固定表格、固定承诺函和人工节点。

### 16.4 编排失败

任何版本 5 写作合同生成失败时：

- 不得退化为空计划后继续纯正文生成。
- 保留旧正文。
- 标记该节点失败。
- 允许用户单独重试计划。
- 整体任务根据安全层规则决定回滚或部分失败。

## 17. 篇幅与扩写

### 17.1 目标篇幅

每个 `SectionWritingContract` 必须包含 `min/preferred/max`。

目标篇幅由以下因素决定：

```text
评分分值或重要程度
+ 技术复杂度
+ 风险等级
+ 证据和表图数量
+ 增值锚点数量
+ 原方案素材量
```

### 17.2 最低字数补足

正文总字数不足时，优先处理：

1. 原子评分点覆盖不足的章节。
2. 高分但内容薄弱的章节。
3. 深度写作章节缺少参数、边界、产物或闭环的节点。
4. 增值锚点未充分展开的节点。
5. 目标篇幅低于 `min` 的节点。

不得仅按当前最短章节排序。

### 17.3 扩写质量要求

扩写必须增加新的有效信息，例如：

- 执行动作。
- 参数和阈值。
- 责任和协同。
- 异常路径。
- 产物和验收。
- 案例化场景，但不得虚构真实案例。

不得仅使用同义改写增加字数。

## 18. 原方案扩写增强

原方案段落除“映射到哪个叶子节点”外，应该分类：

```text
direct-preserve      直接保留
projectize           项目化改写
deep-expand          深度扩写
split-reorganize     拆分重组
material-only        降级为素材
remove               与本项目无关或有风险
needs-confirmation   涉及真实承诺或事实，需确认
```

一段原文包含多个职责时，允许拆分语义后映射到多个节点，但必须保留来源关系和去重，不能把同一原文完整复制到多个章节。

原方案实质段覆盖审计继续默认开启。

## 19. 表格策划

表格必须在写作合同阶段形成 `TableBrief`：

```ts
interface TableBrief {
  table_id: string;
  title: string;
  purpose: string;
  scoring_point_ids: string[];
  columns: string[];
  required_rows_or_dimensions: string[];
  data_sources: string[];
  user_confirmation_fields: string[];
  placement_node_id: string;
}
```

高价值表格包括：

- 项目组织与职责表。
- RACI 职责矩阵。
- 实施阶段与交付物表。
- 里程碑计划表。
- 风险登记表。
- 应急响应表。
- 质量检查表。
- 验收指标矩阵。
- 培训计划表。
- 售后 SLA 表。
- 设备或系统参数表。

不得为了满足“表格较多”而生成与正文重复的装饰表格。

## 23. 取消“一节一图”

### 23.1 必须删除的旧逻辑

- Planner 提示词中的“同一小节只允许编排一张图片”。
- `occupiedSectionIds` 对同一小节后续图片的排除。
- 前端将每类图片数量截断到 `leafCount`。
- 后台将每类图片数量截断到 `eligibleSectionIds.length`。

### 23.2 新的数量决策

AI 根据以下因素决定图片数量：

- 写作类型。
- 章节篇幅。
- 信息类型数量。
- 评分价值。
- 是否为创意方案。
- 图片之间的信息增益。
- 全文图片预算。
- 是否已有表格能更清晰表达。

### 23.3 软密度

| 章节类型 | 建议图片数量 |
|---|---|
| 普通正文 | 0–2 张 |
| 深度写作章节 | 1–4 张 |
| 创意策划章节 | 2–8 张 |
| 固定表格、承诺函、证据节点 | 通常不自动配图 |

该表是软密度。图片不适合时可以为 0；不得为了填满范围制造重复图片。

程序可以设置每小节绝对安全上限 8 张，以防异常计划，但该值不得作为生成目标。

### 23.4 去重规则

同一小节多张图必须具有不同 `visual_role`，例如：

```text
总体概念
执行场景
流程说明
空间布局
主视觉方案
物料延展
进度安排
职责关系
风险控制
效果评估
```

不得仅替换图题后重复相同画面、相同流程或相同业务对象。

### 23.5 跨类型冲突

不再使用固定 `HTML > AI > Mermaid` 作为同小节唯一胜出规则。

新的选择原则：

- 同一信息角色只能保留最合适的一张图。
- 不同信息角色可以同时使用 HTML、AI 和 Mermaid。
- HTML 适合精确结构、数据、流程和矩阵。
- AI 适合创意、场景、空间和视觉概念。
- Mermaid 只适合简单流程、层级和职责关系。
- 同一图意在多个类型重复时，优先 HTML，其次 AI，最后 Mermaid。

## 25. 图片生成和视觉 QA

### 25.1 HTML 图片

生成后必须验证：

- 完整 HTML 文档。
- 不依赖网络和本地任意文件。
- 成功渲染 PNG。
- 无横向溢出。
- 无明显文字截断和重叠。
- 最小正文文字不低于可读阈值。
- 图题、节点和数据来自 Brief/正文。
- 同一投标文件使用统一的字体、配色、圆角、线宽和图注风格。

若检测到溢出、拥挤或截断，必须将渲染诊断反馈给模型或 Agent，最多修复两轮。

### 25.2 Mermaid

继续保留：

- 支持语法白名单。
- 真实本地渲染。
- 失败修复。
- 节点数量和文字长度控制。

Mermaid 默认关闭不代表删除能力。

### 25.3 AI 图片

若供应商或应用具备视觉理解能力，应该执行语义 QA：

- 是否符合图题和 `visual_role`。
- 是否包含必须元素。
- 是否出现禁止元素。
- 是否出现明显乱码、伪 Logo 或无关对象。
- 是否与客户、活动和方案特点一致。
- 是否适合投标文件而非广告成片式过度夸张。

若当前模型不支持视觉审核：

- 不得假装已审核。
- 完成文件、尺寸和生成状态检查。
- 标记为“需要人工视觉核对”。

### 25.4 图文一致性

每张图必须能够回答：

```text
这张图帮助评委更快理解或相信什么？
```

无法回答时不得入选最终计划。

### 25.5 插入与正文引用

在图片计划确定后，章节统稿应在图片前后增加自然引用，例如：

```text
整体实施路径及关键控制节点如下图所示。
```

```text
该流程通过分级判断、责任升级和关闭验证形成完整闭环。
```

不得生成“见下图”但实际图片位于其他位置的错误引用。

# 第六部分：质量审核和评委模拟

## 26. 多维质量审核

最终正文完成后必须依次执行：

### 26.1 合规审核

- 强制要求是否全部响应。
- 固定格式是否保持。
- 否决项是否全部有处理状态。
- 隐性附件要求是否完成路由。
- 人工内容是否仍缺失。

### 26.2 评分覆盖审核

- 每个原子评分点是否有实质正文。
- 高分条件是否明确体现。
- 评委是否能够快速定位得分依据。
- 是否存在只有标题、没有有效内容的评分节点。

### 26.3 技术可执行性审核

- 是否明确责任主体。
- 是否有执行频次或时限。
- 是否有输入、输出和验收标准。
- 是否存在无法实现或过度承诺。
- 深度写作章节是否真正包含参数、边界和产物。

### 26.4 证据审核

- 关键能力是否有材料支持。
- 证明材料是否与评分点对应。
- 真实案例、人员、设备和资质是否来自用户资料。
- 待确认信息是否明确标记。

### 26.5 全文编辑审核

- 章节是否重复。
- 术语是否统一。
- 前后是否衔接。
- 是否存在套话、空话和高频 AI 句式。
- 各章节详略是否与评分价值匹配。
- 增值锚点是否建立在基础响应之上。

### 26.6 图表审核

- 图表是否准确。
- 图表是否与正文一致。
- 是否存在重复图或重复表。

- 当前已生成正文的影响提示。
- 生成后差异预览。

### 31.3 正文填写方式与状态标签

普通正文节点的填写方式由目录项编辑面板中的唯一入口控制：

```text
标题
→ 编辑
→ 正文填写方式
→ AI编写 / 人工填写
```

规范语义：

```text
AI编写：
  response_mode = freeform-markdown
  manual_input_required = false

人工填写：
  response_mode = freeform-markdown
  manual_input_required = true
```

`response_mode` 表示响应内容类型，不得把 `freeform-markdown` 机械翻译成“AI正文”。普通正文节点的显示标签必须由上述下拉框状态统一派生，不新增第二套相互竞争的持久化字段。

左侧目录树和右侧“目录项详情”必须使用同一个共享派生函数，并遵守以下显示优先级：

```text
1. 特殊响应模式节点 → 只显示对应专用标签
2. 普通 freeform 节点且 manual_input_required = true → 人工填写
3. 普通 freeform 节点且 manual_input_required = false → AI编写
```

普通正文节点必须满足：

```text
AI编写 XOR 人工填写
```

二者互斥，任何位置都不得同时显示。界面中不得再出现旧标签：

```text
AI正文
```

特殊响应模式继续显示专用业务标签：

```text
fixed-markdown-table → 固定表格
locked-commitment    → 固定承诺函
evidence-markdown    → 证明材料
explicit-none        → 明确无内容响应
container            → 目录容器
```

特殊响应模式节点：

- 不附加“AI编写”或“人工填写”标签。
- 编辑面板隐藏或禁用“正文填写方式”下拉框。
- 可以继续附加“不可删除、标题锁定、顺序锁定、层级锁定”等独立约束标签。
- 即使旧数据同时包含 `manual_input_required`，显示时仍以专用响应模式标签优先，避免出现“人工填写 · AI正文”或“固定表格 · AI编写”等冲突组合。

保存普通正文节点的下拉框后，左侧目录树和右侧详情必须立即、一致地显示所选的“AI编写”或“人工填写”。

### 31.4 目录树标签

节点可以显示：

```text
高分项
深度写作
增值锚点
待确认
高风险
固定目录
AI编写
人工填写
固定表格

证明材料
明确无内容响应
目录容器
```

显示规则：

- `AI编写` 与 `人工填写` 只能出现一个。

- 约束标签可以与填写方式或专用响应标签并列。
- 标签不得遮挡标题或导致目录树不可用。

### 31.5 高风险区

显示否决项和隐性要求的覆盖状态，支持定位目录节点。

# 第十部分：测试与质量门禁

## 38. 单元测试

至少覆盖：

### 38.1 要求矩阵

- 评分大类拆成多个原子评分点。
- 分值和高分条件保留。
- 来源引用规范化。
- 重复评分点合并。
- 未知评分 ID 拒绝。

### 38.2 增值锚点

- “售后服务”产生应急和持续改进候选。
- “实施进度”产生关键路径、偏差和韧性候选。
- 无相关性锚点被拒绝或降级。
- 无来源的具体承诺进入待确认。
- 同义锚点去重。

### 38.3 三重反查

- 每个原子评分点必须映射。
- 签章否决项路由到 submission，而不是正文目录。
- 固定承诺函路由到 fixed-form。
- 脚注中的附件格式要求被识别。
- 未处理风险阻止普通成功。

### 38.4 深度目录

- 普通子树最多四级。
- 深度子树必须达到五级。
- 深度子树允许部分非关键四级节点保持叶子。
- 非深度子树出现五级时失败。
- 六级目录始终失败。
- 固定和人工节点不能深度写作。
- 子树规模和重复标题审核。

### 38.5 局部深化

- Patch 只修改目标二级子树。
- 现有标题不删除、不改名、不移动。
- 锁定字段不修改。
- 其他正文、计划、图片不失效。
- 旧叶子正文被安全迁移为来源素材。
- 失败时完整保留旧状态。

### 38.6 Content Plan v5

- 所有必需字段校验。
- 指纹变化使计划失效。
- 深度写作 Prompt 包含评分点、锚点、边界、产物和禁止重复。
- 计划失败不退化纯正文。

### 38.7 图片计划 v4

- 新创意类型合法。
- 同一小节允许多张图。
- 同一 `visual_role` 重复被拒绝或合并。
- 30/20/5 硬上限。
- 不再按 leaf count 截断。
- 正文块锚点合法。
- 旧锚点失效时安全退化。
- 关键文字和 Logo 规则进入 Brief。

### 38.8 正文填写方式与标签

至少覆盖：

- 普通 `freeform-markdown + manual_input_required=false` 只显示 `AI编写`。
- 普通 `freeform-markdown + manual_input_required=true` 只显示 `人工填写`。
- 任何状态都不再显示 `AI正文`。
- 左侧目录树和右侧目录项详情使用同一派生结果。
- 编辑下拉框从 `AI编写` 切换为 `人工填写` 后，两处标签同步更新。
- 编辑下拉框从 `人工填写` 切换为 `AI编写` 后，两处标签同步更新。
- 固定表格、固定承诺函、证明材料、明确无内容和目录容器只显示专用标签。
- 特殊响应节点不显示或禁用正文填写方式下拉框。
- 特殊响应模式与旧 `manual_input_required` 冲突时，专用标签优先且不出现双标签。

## 41. 质量评价 Gate

### 41.1 确定性指标

必须达到：

```text
原子评分点映射率 = 100%
否决风险处理状态率 = 100%
隐性要求路由率 = 100%
未知评分 ID = 0
固定目录破坏 = 0
非深度五级目录 = 0
六级目录 = 0
局部深化目标子树外修改 = 0
图片超过硬上限 = 0
同图意重复计划 = 0
安全回归失败 = 0
```

### 41.2 独立质量审核

使用与生成阶段不同的模型或 Agent，对固定 Fixture 按 1–5 分评估：

- 评分命中。
- 内容具体性。
- 技术可执行性。
- 章节边界和非重复性。
- 证据和事实可信度。
- 图表相关性。
- 创意方案定制程度。

每项不得低于 3，核心项“评分命中、可执行性、事实可信度”平均应达到 4 以上。

模型评价必须与人工抽查结合，不得只凭自评模型声称质量达标。

### 41.3 真实外部模型 Gate

若实际发布使用外部文本、Agent 或图片模型，发布前必须在真实配置上执行：

- 至少一份工程类标书。
- 至少一份广告策划类标书。
- 至少一次局部目录深化。
- 至少一次同小节多图。
- 至少一次 HTML 视觉修复。
- 至少一次 AI 创意图片人工核对。

无外部凭据时只能报告本地 Code Complete，不能报告质量 Release Gate 已通过。
