## 0. Codex 执行入口

先阅读仓库根目录及修改范围内的 `AGENTS.md`，再执行本文第 12 节的任务。先完成基线核查、影响分析和针对性测试，再进行局部修改。除非出现权限、数据安全、重大规格冲突或必要信息缺失，不需要每做一步都等待用户确认。

本次不是重写目录系统，也不是重新编制一份招标响应文件。修改对象是现有目录组织规则及其关联链路。本文确认的产品规则替代旧文档中相冲突的“强制下沉”“最多五个”“拆分后必须补足两个”等业务约束，其余来源保护、人工编辑保护、安全规范和运行约束继续保留。

不要执行 `reset --hard`、强制切换、清理未提交文件、覆盖工作区、强推、自动合并或自动发布。不要把本文中的示例结构硬编码为产品模板。

## 1. 依据、问题与结论边界

### 1.1 用户已经确认的产品方向

用户明确接受：同一章中，有的三级标题直接写正文，有的继续展开四级，重点内容必要时再展开到五级。随后对配套建议表示基本同意，并要求形成 Codex 实施文档。

据此，本轮将以下事项纳入实施：混合深度、按内容判断拆分、取消“超过五个就必须重组”的业务硬限制、标题与内容要求分开、生成与修复规则一致、正文与导出兼容、人工复核与操作留痕。

这不意味着取消最大深度、取消重点章节限制、取消字数设置、自动合并历史目录，或扩大到整套投标文件合规系统重构。

### 1.2 输入样本支持的观察

样本 Word《商务技术文件大纲_1789896759184828312.docx》中，“多项目并行管控”“紧急及突发处置”“全流程沟通对接图示”“沟通响应时效”等不同复杂程度的主题，都展开为两个下级标题；现场管理和售后服务部分也存在相同模式。[S1]

本轮需要解决的是这种跨主题的机械拆分倾向，而不是把所有“两个子标题”判错。合理的二分结构可以保留。

招标 PDF 仅用于核对具体示例和建立回归样本，不应把这个项目的名称、时限、材料参数或章节数量固化为通用产品规则。[S2]

旧版提示词函数或前端副本即使包含“两项示例”，也不能未经调用链核实就归为当前主流程根因。只修改实际可达路径或确需同步的同源规则，不顺手清理整个历史架构。

## 2. 用户故事与成功标准

| 用户故事                            | 用户需要的结果                     |
| ------------------------------- | --------------------------- |
| US-01：作为编制人员，我希望简单事项直接写，复杂事项再拆分 | 不再为填满统一层级反复删标题、合并正文         |
| US-02：作为编制人员，我希望目录简洁但要求完整       | 减少标题后，参数、时限、交付形式和评分事项仍有明确承接 |
| US-03：作为审稿人员，我希望合理的不同层级正常工作     | 三级、四级、五级叶子都能编辑、生成、统计和导出     |
| US-04：作为已有项目的维护者，我希望升级不破坏已完成工作  | 历史目录、人工内容、附件与配图不被后台自动重组     |

成功不能仅用“两个分支比例下降”“总标题减少”或“字数变短”判断。核心是每个新增标题有独立作用、没有因拆分或合并丢失要求，而且整个编辑与导出流程可用。

## 3. 范围与非目标

### 3.1 本轮必须覆盖

现有来源驱动目录生成、JSON/结构修复、目录字数规划调整、实际可达的知识库补目录、正文最低字数补目录、只读语义审查，以及混合深度在保存、编辑、正文生成、统计、配图和 Word 导出中的兼容性。

只对不满足新规格的位置进行修改。已经按真实叶子递归处理、且测试证明正常的组件不需要重写。

### 3.2 本轮不做

不更换模型供应商，不靠提高 temperature 或随机化解决结构问题；不更改最大深度的既有产品边界；不改变重点判定的分档口径；不重写招标解析、全局事实、表格还原或 Word 排版引擎；不建立新的复杂评分责任矩阵或审批中心；不增加全新目录模式选择器；不改管理端、授权、更新下载、CI/CD、发布制品和 Analytics。

第一次审查中发现的商务材料缺位、偏离表与方案混写、章节同名、源编号混入标题等问题，不因此自动纳入本轮全面修复。与本轮直接有关的固定来源及响应形式必须保护；其他问题另列后续清单。

### 3.3 实现方式

这次限制存在于现有 Electron 程序的提示词、校验和任务链路内，单独配置无代码工具无法解除。因此由 Codex 在现有代码内局部实现，不引入飞书、Zapier 等外部运行依赖。人工对比与验收可以使用现有文档或表格记录，与产品实现解耦。

## 4. 目标业务规则

以下 R 编号作为开发、测试和验收的统一引用。

### R-01：先判断内容，再判断是否拆分

先识别当前节点必须响应的事项，判断是否值得分别编写独立正文，再决定标题结构。一个完整事项可以通过自然段、表格、图示或步骤说明写清楚时，允许当前节点直接作为叶子。

“包含多个内容点”“属于一个评分点”“是重点章节”都不是自动增加层级的充分理由。

### R-02：允许同章不同深度

AI 新增结构中，三级可以直接承载正文，四级可以直接承载正文，重点章节必要时可以出现五级叶子。不同分支允许采用不同深度；不要求每章同时出现三种深度，也不要求每章到达最大深度。

来源本来规定的一、二级表格、承诺、附件或其他浅层叶子继续保留，不能为了达到三级而强行扩展。

AI 新增节点最大深度仍为五级；新增五级仍受现有重点章节规则约束。来源原有结构按既有来源保护处理，不能为符合 AI 新增规则而改写。

### R-03：独立成节的判断

新增子标题应当能说明自己负责回答什么，并与兄弟小节有清楚边界。可采用的判断依据包括不同任务、不同处置情景、不同交付物或确需分别展开的执行方法，但不能机械套用这些维度。

每个细参数、检查点、一句承诺、几步操作，不应自动变成独立标题。同一个要求存在多个独立情景时，不得为了保持两个分支而挤掉第三个情景。

“内容有关联”不等于“必须新增共同父标题”；原父节点已经充分表达共同主题时，无须再加一层同义包装。

### R-04：子标题数量由内容决定

不设置统一目标数量，不默认两个，不改成统一三个、三至五个或随机数量。合理的两个保留，合理的三个或更多也保留。

不采用“两个分支占比不得超过某值”作为通过标准。数量统计只能辅助检查，不能直接驱动增删标题。

### R-05：单分支优先消除多余层级，不补齐

对本次生成、尚未保存且不含来源或用户内容的 AI 新增结构，如果只有一个实质子项，提示词应优先让当前节点承载完整事项，不再套一个父子空壳，也不得编造第二项。

**本轮实现口径：单个子节点不再作为“必须补足两个”的结构错误。**可作为语义质量提醒。只读审查不得自动压平；也不新增一个自动压平历史目录的功能。首次生成与现有修复调用可以在受保护边界之外优化候选结构。

来源规定的单分支、人工编辑结构、已有正文或附件关联结构，不适用自动合并。

### R-06：超过五个不再强制重组

同一二级目录下，六个或更多真实独立的三级叶子可以通过校验并保存。取消原先仅因第六项出现而报错、重试或强制增加父层的规则。

数量较多可以进入归类检查，但只有存在重复、职责不清或自然分类能改善阅读时，才给出具体建议。不能仅依据“超过五个”给出质量不合格结论。

这不取消现有任务总节点数、JSON 大小、上下文长度、超时和资源保护边界；不得把这些工程边界改造成凑标题规则。

### R-07：标题和写作要求分离

标题表达主题，既有 `description` 或当前等价的节点说明字段承载应写内容、关键边界及必要交付形式。优先复用现有数据契约，不新增一套大型结构字段。

节点说明需要具体到本节。不能只把标题换句话说，也不能把全书通用写作原则复制到每个节点。没有必要固定成若干个标签或两条说明。

需要图示或表格的响应事项，即使不增加子标题，也必须在节点说明中明确保留其交付形式。不得把节点说明、内部审查记录或调试标签直接当作投标正文导出。

### R-08：减少层级不能减少要求

拆分时，应明确每个独立要求由哪个叶子主要承接。合并时，要保留原来各项具体要求，不能只保留更概括的标题。父级适用于所有子节的背景或共通边界可作为祖先上下文；只属于某一子节的细项应进入对应叶子，不得要求所有兄弟章节重复展开。

优先沿用现有说明字段、可信评分标记和来源引用。不为本轮恢复已废弃的质量字段，不伪造需求 ID 或来源锚点。

覆盖检查必须有实际输入依据；仅有标题不能证明完整覆盖。缺失原要求或详细评分上下文时，应写明无法核实，不得给出“全部覆盖”的保证。

### R-09：固定来源和响应形式优先

保持冻结来源节点的标题、相对顺序及层级。允许在现有规则允许的叙述性来源节点内部补充必要内容，不代表允许移动、重命名或删除来源节点。

已明确属于固定表格、承诺函、证明或附件的节点，不得为了数量和深度要求变成一组文章。必需原文和表格内容按现有机制保留；本轮不承诺修复全部历史格式问题，也不新建文档类型识别引擎。

来源信息不足、无法安全判定是否可以重组时，保留结构并提示核对。

### R-10：用户内容与历史项目不自动迁移

人工编制节点及其后代、已有正文、图片、附件、用户自建或手改结构，不因升级、打开项目、运行审查或补目录而自动重组。保护不能只看当前节点的人工标记，还须继承祖先保护范围。

新规则适用于之后的新生成，以及用户明确启动的重新生成和既有补充流程。用户明确选择全量重新生成时，沿用现有清空正文与计划的产品契约，但必须使用既有清楚的提示和确认，先保证可恢复副本，不把本轮升级视为覆盖授权。

### R-11：全部可达生成链路遵守相同原则

首次生成、修复、字数调整、知识库补目录和正文补目录都遵守 R-01 至 R-10。不同入口保留各自输入输出契约，不能因为规则共享就让“增量补丁”返回全量目录。

新增内容不得改变既有人工/AI 编制选择的产品语义；不要把所有节点强制设为人工，也不要清除用户已设置的人工标记。

### R-12：字数目标继续保留，但不以空标题凑数

保留用户已有最少字数、最多字数、每节目标及严格模式的设置含义、默认值与本轮开始时的折算口径，不擅自降低目标或重新分配字数。

字数调整只能寻找有实际独立内容的增补机会，或在不丢要求的前提下合理合并。不得强行下沉、虚构业务、制造同义小节来凑叶子数量。

当内容自然结构与字数目标冲突时，使用现有有界调整与提示机制，明确显示未达目标和原因，交由用户决定下一步。禁止无限重试，也不能把未达目标标为已满足。大范围字数预算改革不在本轮范围内。

## 5. 提示词修改规格

### 5.1 统一规则正文

下面是目标业务规则文本，不是要求把整份规格书发送给模型。Codex 应将其压缩整合进现有提示词，确保含义不丢失；不要重复注入多次。

```text
目录自然拆分规则：
1. 来源骨架已有节点的标题、层级、顺序保持不变。仅优化本次允许新增或调整的 AI 目录，保护人工节点、其后代和已有内容。
2. 先确定当前节点需要响应的具体事项，再判断是否有必要增加子目录。能在当前节点内完整说明的，直接作为正文叶子。
3. 只有存在多个可独立展开、边界清楚且不会互相重复的事项时才拆分。参数、检查点、步骤或一句承诺，不因数量多就自动升级为标题。
4. 子目录数量由内容决定，不默认两个，不设统一目标数量，也不为追求数量差异随机增删。
5. 允许同一章不同分支深度不同：三级和四级均可为叶子；重点章节确有需要时可到五级。最大深度和重点资格按当前约束执行，不要求达到最大深度。
6. 只有一个实质子项时，优先由当前节点承载，不补造第二项。不得据此合并来源或用户保护的节点。
7. 同一二级下超过五个独立三级叶子不是错误。有合理共同主题且新增分类有价值时才归类，不能仅因数量触发重组。
8. 标题只表达主题；节点说明保留该节应写内容、关键参数或边界、必要交付形式。减少标题不能减少响应事项。
9. 拆分后各叶子的职责应清楚；共同背景通过祖先上下文承接，不要让多个兄弟节点重复展开同一完整内容。
10. 不把固定表格、承诺或附件改写成方案章节。不得虚构人员、业绩、证书、资源、事实或额外承诺来填满结构。
11. 不为满足字数或目录整齐而制造无实质内容的标题。信息不足时保留现有要求并说明不足，不自行补成已知事实。
12. 输出遵守当前任务的 JSON 字段和操作范围。只返回任务要求的结果，不输出思考过程、解释或正文。
```

### 5.2 各阶段附加规则

| 阶段        | 必须增加或调整的指令                       | 必须保留的边界                 |
| --------- | -------------------------------- | ----------------------- |
| 初次下级补充    | 允许直接生成三级叶子；节点说明不能因不拆分而简化成空泛句     | 冻结来源、字段、编号和重点条件         |
| JSON/结构修复 | 优先修复真实结构错误；不得将“补一个子标题”作为单分支通用修法  | 不越权删除来源或用户内容；保持原任务结果形状  |
| 目录字数调整    | 在有实质内容前提下调整；无法兼顾时保留目标未达信息        | 用户设置、调整次数上限、来源与人工保护     |
| 知识库增补     | 可补节点说明或追加独立小节，不必须新建父层；无新增价值返回空补丁 | 既有追加/更新范围、父节点引用、禁止完整覆盖  |
| 正文阶段补目录   | 新增三级叶子合法，正文已写节点及其受保护子树不可拆        | 已有内容、全局事实、任务状态和编号关联     |
| 最终语义审查    | 检查拆分必要性、父子空转、兄弟重复、合并后遗漏和职责边界     | 只读、不修改目录、只返回既有审查 Schema |

### 5.3 JSON 示例的使用

示例只说明数据结构，不表达推荐分支数量。不要把示例全部写成二分树，也不要用“每个案例必须不同数量”的新模板。

至少有一个合成测试样例表达混合深度，示意如下。名称与数量只服务测试，不属于招标规定，也不能硬编码进业务提示词：

```text
技术方案〔一级〕
└─ 服务方案〔二级，具备重点资格〕
   ├─ 沟通响应时效〔三级叶子〕
   ├─ 现场保护与清理〔三级组织节点〕
   │  ├─ 既有设施保护〔四级叶子〕
   │  └─ 清理清运与环境恢复〔四级叶子〕
   └─ 应急处置〔三级组织节点〕
      ├─ 需求变更处置〔四级叶子〕
      └─ 现场突发处置〔四级组织节点〕
         ├─ 作业暂停与现场隔离〔五级叶子〕
         ├─ 情况确认与方案调整〔五级叶子〕
         └─ 恢复作业前复核〔五级叶子〕
```

该合成结构有 7 个叶子：1 个三级、3 个四级、3 个五级。组织节点不应仅因处于某一级就另建正文任务。该例不用于判断真实项目一定需要上述拆分。

## 6. 程序校验、语义审查与修复边界

### 6.1 把确定性错误与写作建议分开

| 情况                                     | 目标处理                          |
| -------------------------------------- | ----------------------------- |
| JSON 形状错误、非法 children、非法/冲突节点引用、超出操作范围 | 维持结构校验及既有有界修复，不放宽真实错误         |
| 改动冻结来源或人工/已有内容保护范围                     | 拒绝此次越权变更，保留已有有效内容             |
| AI 新增超过五级；非重点范围新增五级                    | 按现有产品深度规则拒绝；来源已有节点另按来源保护处理    |
| 三级没有 children                          | 合法叶子，不触发补齐                    |
| 三级或四级只有一个子节点                           | 不再因“必须两个”硬失败；列为可读性检查，不自动补第二项  |
| 同一二级下六个或更多新增三级叶子                       | 不因数量硬失败；可以检查内容关系，不强制归类        |
| 多处恰好两个分支                               | 不是确定性错误；只有结合内容发现机械拆分，才给出具体问题  |
| 父子同义、兄弟职责重叠、某个必答事项没有承接                 | 语义提醒，给出节点和具体原因；不得声称由简单数量校验证明  |
| 语义审查超时、不可用或上下文不足                       | 保留既有降级策略，显示未完成/无法核实；不得伪装为审查通过 |

移除旧数量硬限制时，不能通过跳过整个 `validateSourceDrivenOutline()` 或质量检查来实现。保留来源、类型、权限、深度和任务安全检查。

### 6.2 审查输入必须足够

只读审查至少应获得当前候选目录、有效来源骨架、已有项目概述，以及本次实际可用的技术要求/评分说明。可在已有任务工作区的审查上下文文件中补充这些输入，不需要建立新的数据库模块。

规则：完整检查某项要求需要读取它的实际文本。若只有概要，则只对可见内容作判断，并明确审查范围。大上下文按现有分段或裁剪机制处理；不能悄悄截断必答要求后宣称覆盖。

继续沿用当前 `passed`/`warning` 和既有不可用状态，不要求 Agent 返回修改后的目录、不增加新的状态机、不绕过现有 JSON Schema。

### 6.3 不增加无界模型调用

复用现有生成、修复和最终只读审查。拆分质量提示不能触发无限“生成—审查—重写”循环。本轮不默认新增一条全量自动重写链路，也不额外多次调用模型追求数量分布好看。

## 7. 正文、编辑、统计与导出兼容

### 7.1 叶子判断以实际树结构为准

叶子是没有实际子节点的节点，不是固定第三级、第四级或第五级。AI 正文目标还须满足当前人工编制、范围选择和内容状态的条件。

需要分别测试 `children` 缺省与空数组；非法数据应在数据校验阶段被处理，不能为了“允许叶子”将任意错误值都视为合法。

人工节点及其后代不得进入 AI 生成、扩写或自动配图覆盖范围。人工节点是否计入完成率、字数等，沿用当前定义并验证不退化。

### 7.2 节点说明与祖先上下文

三级叶子必须和四、五级叶子一样获得本节说明、祖先标题/说明、相关需求、全局事实等当前应有的输入，不得因为没有更深层级而少传上下文。

父级承载的共通要求需能传递至相关叶子，但不得把全部兄弟节点职责复制成每节的硬性必写内容。主要细项由叶子说明明确承接，祖先只提供有用背景和共通边界。

父级是否有导语、已有正文如何展示，沿用现有行为，不在本轮新增父级概述生成系统。若历史父节点已有内容，不得因为它不是叶子就清除或从导出中丢弃。

### 7.3 必须走通的链路

验证保存与重开、目录树编辑、人工/AI选择、全量生成、单节重生成、扩写、取消/恢复、字数统计、进度统计、配图计划、正文导出和仅目录导出中所有实际存在的入口。

修改只针对真实存在的固定层级假设。不得为了支持混合深度而默认重写配图引擎、生成并发、排版样式或模板设置。

### 7.4 编号与引用安全

不能假定当前 `id` 是与显示编号无关的稳定身份。Codex 需核查编号与正文、计划、图片和缓存的实际关联。

首次未保存候选可以沿用现有统一编号；在已有内容上的增补必须保持现有安全引用更新方式。不得仅靠标题匹配既有内容，不得让重新编号把正文或图片绑定到另一个节点。

已有内容节点不被拆分或移动是本轮重要边界。活动正文任务运行期间，不擅自应用会改变其目标集合的结构重组。

## 8. 保护、人工审核与操作留痕

### 8.1 人工确认不变成逐节点弹窗

复用现有骨架确认、目录编辑和审查展示。生成过程不对每个合理实施方法或每个标题拆分新增确认弹窗；用户在目录阶段及导出后的人工复核继续保留。

只读审查给出具体节点问题，不静默改目录。现有界面无法显示必要提醒时，仅补充最小展示，不新增复杂审批流程。

### 8.2 既有项目及失败保护

升级和打开项目不迁移旧目录。知识库或正文补丁失败，保留旧的有效状态。全量重新生成只有在用户明确操作后按既有契约处理，先使用现有备份/项目副本机制保证可恢复。

若本地缺少可恢复措施，实施报告应明确这一风险；在对用户真实项目进行破坏性验证前先建立副本。不得将任务失败后的半成品覆盖为已确认结果。

### 8.3 留痕与隐私

优先复用现有任务日志及开发日志，记录任务 ID、代码提交、规则版本或摘要、模型标识、已有生成参数、字数设置、生成/修复/增补阶段、节点与叶子统计、告警以及失败/降级原因。

统计区分各层叶子数量及同级子项分布，用于诊断，不作为数量配额。对实际应用的补丁记录受影响节点和变更摘要；全量请求/响应仅在已有授权调试能力允许时保留，并遵循现有本地保存与清理策略。

不得把 API Key、授权令牌、人员证件、银行信息或完整私有招标材料写入公共日志、仓库或新的外部服务。测试优先使用合成数据；真实样本保留在本地忽略目录，不因本轮任务上传到仓库或公共 CI 制品。

### 8.4 内容边界

不新增与本项目无关的敏感表述、竞争对手名称、虚假人员/业绩/证书或未经依据的资源承诺。允许补充合理一般方法，但不能把它们写成已发生事实或招标文件明确规定。

既有内容校验继续保留。本轮不新增全局关键词过滤引擎，也不对来源标题、承诺原文或法定术语进行无差别删改。来源中的冲突由人工核对，不以自动替词破坏响应完整性。

### 11.2 真实样本 A/B 验证

使用用户提供的 Word 作为问题样本，使用同一招标 PDF 及相同的有效解析上下文作为生成输入。比较时保存原始基线，不在真实已编制项目上破坏性运行。

固定模型标识、模型配置、来源骨架、字数设置、知识库选择和其他可控输入，仅变更本轮规则及必要关联校验。记录无法固定的条件，不把模型随机差异误认为改进。

先做一次修复前后对照；经现有预算允许，可扩展为每组最多三次观察，不得把自动反复生成当作默认无限试验。真实调用使用用户已有授权配置；无可用凭证、样本或预算时标记待验证，不编造结果。

| 观察项                      | 记录方法                   | 判定原则                 |
| ------------------------ | ---------------------- | -------------------- |
| 三级/四级/五级叶子数量、总叶子数、分支数量分布 | 记录原始统计                 | 不设置美观配额；同质分布只作线索     |
| 标题是否独立、是否父子同义            | 人工逐项标记具体例子             | 不以关键词或标题数替代语义判断      |
| 关键要求与交付形式是否有承接           | 对照来源，填写“要求—目标节点/说明—结果” | 有遗漏须指出；不能用标题相似宣称覆盖   |
| 正文是否重复或漏写                | 选择有代表性的三级、四级、五级叶子实际生成  | 重点验证时限、具体情景与图表形式     |
| 模型调用次数、耗时、token 用量、失败/重试 | 能取到则记录；不能取到写未记录        | 不把不可见指标估算为实测         |
| 人工删标题、合并正文及补漏耗时          | 同一审稿口径记录               | 用于后续评价实际节省时间，不预设收益数字 |

### 11.3 样本对照重点

“全流程沟通对接图示”可以不继续拆，但说明必须保留从需求接收到售后服务的流程、信息路径、责任人和对接方式。“沟通响应时效”可以直接写，但必须保留来源规定的确认时限及处置反馈要求。[S1][S2，印刷页 95]

“紧急及突发处置”要核查来源列出的不同情景是否仍被覆盖，不规定必须采用某三个标题。“现场保护与清理”本来包含不同阶段任务，合理保留两个子标题不算失败。[S2，印刷页 95]

“完工验收量尺照片要求”的丈量、质量、画面完整性、全局与细节照片要求可以由一个小节内的说明/表格承接，不能因减少标题而漏掉。[S2，印刷页 34—35]

这些是结构效果回归，不是重新进行完整投标资格、报价、样品或法律合规审查。
