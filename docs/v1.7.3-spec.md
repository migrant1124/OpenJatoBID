## 1. 已确认的产品决策

以下为本轮不可被技术实现擅自改变的需求基线。

| 编号 | 已确认决策 |
| --- | --- |
| D01 | 正文应接近专业人员编写投标文件的表达：逻辑清晰、语句通畅、语言清楚，不追求通过所谓“AI检测”。 |
| D02 | 以连贯自然段承载解释和论述，不把全文写成“我们……”“我们……”的短句清单。 |
| D03 | 实施方法需要适当展开，但必须简洁、清晰，让评委容易看见关键做法。 |
| D04 | 前后衔接必要，但应简短自然，优先用业务关系衔接，不增加空泛的过渡段。 |
| D05 | 可以使用表格、步骤、合理列表和简短加粗引导语；不允许从“全部清单化”走向“全部长段落化”。 |
| D06 | 招标文件未详细规定的一般实施方法，允许AI合理补充，前提是可执行、与项目相符、不违背已知要求。 |
| D07 | **一般方法直接进入正文，生成过程中不逐项确认、不弹审批框、不暂停等待用户决定。** |
| D08 | **不因一般方法补充或文风诊断新增导出前确认、审核关卡或阻断条件。用户导出后在文件中自行审阅、修改和确认。** |
| D09 | 允许补充做法不等于允许虚构人员、设备、资质、业绩或新增具体数量、时限、质保等承诺。 |
| D10 | 普通正文的优化不得误改招标固定表格、承诺函原文、必要重复响应、人工填写内容和已有有效技术信息。 |

### 1.1 审核边界

用户已授权“一般实施方法”的自动补充，不需要开发时重新设计审批制度。导出后的人工审核是用户工作方式，本版不实现审核状态回传，也不声称能知道用户是否已经完成文件外审阅。

现有任务错误、必要资料缺失、人工编制节点等机制维持原有职责；不得借本轮需求新增审批，也不得借“导出后审核”绕过既有安全限制。

### 1.2 版本边界

只读基线的 `client/package.json` 显示 `1.5.2`，这仅说明核对到的远端源码状态，不代表用户实际安装版本或本地最新代码。目标版本按用户指定采用 **1.7.3**。

Codex 必须先核对本地分支和真实实现，再应用本规格；不得为了与本文件行号、函数名或版本一致而回退用户代码。若本地已经包含 1.7.3 的其他改动，采用增量实现，不覆盖已有工作。[S01][S02]

## 2. 问题定义与源码依据

### 2.1 用户观察到的问题

**问题A：反复介绍相同背景。** 不同小节反复出现采购单位、合同签订单位、项目管理单位和投标人关系的介绍。文字虽然可能准确，却没有推进当前章节的任务。

**问题B：正文碎片化。** 大量内容被拆成“我们准确呈现……”“我们统一控制……”等孤立短句，缺少动作之间的联系，读起来像检查清单。

**问题C：方法展开不足。** 有动作名称，却缺少必要的处理方式、判断或交接说明；单纯把短句合并，仍不能解决实质内容不足。

### 2.2 已核对的源码情况

| 位置 | 已确认的情况 | 本轮处理方向 |
| --- | --- | --- |
| `contentGenerationTask.cjs` / `buildChapterContentMessages()` | 主提示词包含“每句话不超过30个汉字”“必须用句号拆分”、固定主语、连接词禁用和词汇强制替换等规则。 | 删除错误硬约束，改为完整表达、自然句式和事实边界。 |
| 同上 / 正文消息组装 | 向每节提供项目概述、所选事实及本节编排要求。 | 区分“供理解的背景”“提及时必须准确的事实”“本节必须写出的内容”。 |
| 同上 / `buildChapterContentPlanMessages()`、`formatContentPlanForPrompt()` | 已有章节职责、实施步骤、事实选择、跨章节边界及禁止重复字段；并非完全没有编排。 | 强化既有字段语义和实际传递，不另起一套平行编排系统。 |
| 同上 / `buildWritingProfileRequirement()` | 深度写作要求覆盖较多执行要素。 | 改为按章节需要选择展开，不把检查项全部照搬成最终正文。 |
| 同上 / `buildContentExpansionMessages()` | 扩写使用独立提示词，返回局部 `insert/replace` 操作。 | 扩写的新增文字遵循同一文风，但保持原有补丁协议和精确锚点。 |
| `sectionWritingContract.cjs` | 已有计划结构、指纹和提示词版本机制。 | 区分结构兼容与策略过期，避免改文风时破坏历史正文或原方案映射。 |
| `contentQualityAudit.cjs` | 重复检查主要比较不同小节开头最多120个字符是否完全一致。 | 增加段落及近似重复候选诊断，不仅检查开头，不直接据相似度删文。 |
| `contentResponseModes.cjs` | 明确拒绝AI修改人工编制节点。 | 必须保留并覆盖所有相关写入入口。 |

上述为静态源码事实。[S03]—[S08] “重复背景是否由某次具体输入、模型或后处理造成”，仍需用运行日志和样本文档验证。本版不以未经验证的推断扩大改造范围。

## 3. 目标、范围与非目标

### 3.1 目标

交付同一套正文表达标准，贯穿首次生成、单节重新生成、已有方案优化扩写、最低字数扩写和必要的局部修订。

最终正文应同时满足：

- **读得顺：** 相关信息组织成完整段落，因果、顺序、条件和转折清楚。
- **看得见：** 实施方法有关键动作和必要处理方式，重点不过度埋在长段落中。
- **不重复：** 本节承担自己的职责，不反复完整介绍项目背景。
- **不越界：** 一般方法可补充，既有事实和具体履约承诺不可虚构或擅改。

### 3.2 本版范围

本轮属于既有客户端生成链路优化，采用 Codex 修改现有代码。无需新接飞书、Zapier 等平台：外部流程无法直接替换当前运行提示词，还会增加资料流转和重复状态管理。本版不增加无代码审批或外部数据同步环节。

优先修改 Electron Main 侧真实运行入口、共用提示词构造器、章节计划格式化、质量诊断及测试。Renderer 仅在现有状态或类型兼容确有需要时做小范围关联调整。

### 3.3 非目标

不新增文风选择器、方法审批按钮、导出前审核页或新的一级入口；不新增全文必跑的AI润色服务；不重建评分体系、目录层级策略、知识库、图表引擎、Word导出引擎、模型路由、授权或发布体系。

不默认修改独立的 Jato Agent 对话提示词库、视觉工作室或其他功能。只有真实被技术方案正文链路调用的 Agent 分支，才纳入本轮统一规则。

不批量重写历史项目，不自动把所有旧正文迁移为新文风，不对招标原文和已填写材料做全局词汇替换。

## 5. 功能与写作规格

### R01. 替换不恰当的“去AI味”硬规则

必须从**真实运行的正文写作提示词**中移除下列强制要求：

1. 每句话不超过30字、超长必须按句号拆分。
2. 全文主语只能是“我们”“我方”或系统、设备名称。
3. 全面禁止正常连接词、目的状语、被动表达或将来表达。
4. 将“我们将”等一律替换成“我们采用／我们配置／我们基于”。
5. 将“确保、加强、完善、丰富”等机械替换为阈值、数量或已完成配置。
6. 所有服务优势必须统一改成风险损失视角。

替换为正向标准：句长随语义自然变化；一个段落围绕一个主要问题；相关条件、动作和结果应保持联系；避免连续重复同一种句式；有依据地具体表达，不用空泛形容词代替做法。

**限制：** 不得改成“每段至少N字”“正文必须达到某个自然段占比”“每节必须三个加粗主题”等新模板。字数、短句率、列表密度只能作为诊断信号，不能成为写作硬约束或导出门槛。

不能仅在旧规则后追加“语言自然”一句。互相矛盾的旧强制指令必须删除或重写。文档中的问题引用和测试反例可以保留，不得用全仓库字符串删除误改历史资料。

### R02. 正文、重点与列表的表达分工

- 解释、分析、方案论述和相关动作之间的说明，以自然段为主。
- 有明确顺序的流程可用步骤；真正并列且独立的检查项可用列表。
- 职责、参数、任务对照适合表格时，继续遵守用户原有表格设置。
- 实施方法需要快速定位时，可用“文稿核对。”“版面设计。”等简短加粗引导语。
- 加粗引导语是辅助表达，不是每节必填，不替代程序管理的章节标题。

继续遵守已有正文不自行生成 Markdown 章节标题、不重复程序目录编号的约束；不得为改善文风改变目录编号或自动增加目录层级。

不得通过简单删除项目符号、拼接换行、替换句号等后处理“修复”文风。它们可能破坏真正的步骤、表格和句意。

### R03. 实施方法的展开标准

内部编排应考虑：需要解决什么问题、关键动作是什么、怎样处理，以及必要的判断、复核或交接。最终正文按语义组织，不逐项展示内部字段。

**标准写作：** 说明主要做法和关键处理方式，到能够理解为止。

**深度写作：** 在标准写作基础上，只对重要环节增加有价值的适用条件、异常处理、责任协同或交付检查；不得把所有措施统一写成“场景—人员—频次—参数—记录—验收”流水账。

**创意策划分支：** 若实际运行中已有此分支，保留客户特点、受众、主题、创意策略和载体适配等要求，不强行改成设备配置与风险阈值说明。本版不新建或重新路由创意策划模式。

章节编排字段必须完整，不等于每个字段都必须有内容。不适用的量化、证据、交付或其他数组应允许为空；不要为凑字段自动生成“频次待确认”“阈值待确认”或虚构参数。

已有用户字数设置继续有效，但扩写必须增加实质信息。已无可补内容时沿用现有任务结果表达和重试上限，保留已生成正文，不编造细节、不无限重试，也不假报达到了字数目标。

### R04. 一般实施方法允许自动补充

| 分类 | 可以怎样写 | 禁止怎样写 |
| --- | --- | --- |
| 一般流程 | 接收资料、核对文稿、汇总疑问、确认版本、校样对照、交接制作、问题复核。 | 为每个方法增加“待用户批准”的提示或审批状态。 |
| 组织方式 | 合理描述资料归口、意见汇总、交接核对等一般安排。 | 虚构已有部门、已到岗人员、专职人数或人员姓名。 |
| 质量方法 | 描述核对对象、发现问题后的处理和必要复核。 | 无依据新增合格率、检测频次、抽样数量、免费返工范围等具体承诺。 |
| 时间关系 | “文稿确认后”“进入制作前”“修改完成后”。 | 无依据承诺“两小时完成”“全年24小时响应”等时限或服务等级。 |
| 企业能力 | 引用资料支持的现有能力。 | 把拟采用的方法改写成“已经建立”“已部署”“已配备”的既成事实。 |

一般方法必须属于当前采购范围、与已有流程相容、在已知条件下合理可行，不得暗中增加驻场服务、额外设备采购、无限次修改等服务范围或显著资源承诺。

**输出规则：** 一般方法以正常方案语言直接写入正文，不带“AI建议”“建议用户确认”“以下为补充方法”等生成过程说明。不建立逐条方法审批对象。

**缺失事实例外：** 证书编号、人员姓名等必须有确切值的资料项，按既有人工填写或缺失信息流程处理；不能因本规则改为虚构，也不能将普通方法误判为必须填数值的资料项。

### R05. 事实准确与背景复述分开处理

发送给模型的上下文必须明确区分三种用途：

| 上下文用途 | 行为 |
| --- | --- |
| 项目背景 | 供理解项目与主体关系，不默认逐节写入。 |
| 已知事实约束 | 正文涉及该事实时保持准确；“提供给模型”不等于“必须全部输出”。 |
| 当前章节必须响应事项 | 在本节明确回答，不得因去重而省略。 |

保留全局事实选择机制，不为了减少重复而删除必要的周期、地点、主体、人员或质量要求。

项目信息、招标约束和已确认全局事实之间的关系沿用既有来源与冲突处理。对互相矛盾的资料不能自行挑选一个，也不能通过改写文风掩盖事实冲突。

**示例：** 在“服务启动安排”中可以写明向实际负责确认的主体提交资料，但无需重复采购单位、签约单位、项目管理单位和投标人的完整关系介绍。

### R06. 章节职责与前后衔接

复用 `section_role`、`must_answer_questions`、`implementation_steps`、`cross_section_boundaries` 和 `forbidden_repetition`，让当前小节围绕自己的问题展开。

具体要求：

- 同级章节已经负责的事项，本节只保留与当前方法直接相关的交接或引用，不再完整展开。
- `cross_section_boundaries.excludes` 与 `related_node_ids` 不能停留在存储里，必须在适用的写作上下文中发挥作用。
- 不把上一节全文作为本节开头；只在必要时以一两处业务关系自然承接，不规定每节必须有过渡句。
- 不随意写“如前文已确认”，尤其在并发生成、前节未成功时，不得把计划中的内容说成已经完成的正文事实。
- 引用章节号时必须存在、稳定；不确定时用自然语义衔接，不编造交叉引用。

**重复豁免：** 招标要求独立响应、固定表格、承诺函原文、必要术语、主体名称及必须准确重述的指标，不因与别处相同而删除。不能将“公司名称在多节出现”直接认定为不合格。

### R07. 所有相关写入路径遵循一致规则

| 路径 | 必须生效的规则 | 不得破坏的边界 |
| --- | --- | --- |
| 首次生成、单节重新生成 | 自然叙述、清晰方法、背景使用边界、合理补充方法。 | 本节职责、事实和评分响应。 |
| 已有方案还原后的优化扩写 | 同上，并改善必要的衔接与重复表达。 | 保留原方案实质信息、技术路线、参数、承诺、表格及来源映射；不是从零换一套方案。 |
| 最低字数扩写 | 只补充真实缺口，新增文字遵循相同表达标准。 | 不靠背景复述凑字数，不改变既有插入/替换协议。 |
| 原方案覆盖修补 | 补回缺失内容时保持自然表达。 | 不删除或改写需要保留的原有事实。 |
| 一致性修复 | 局部纠正冲突时保持上下文自然。 | 一致性审计仍只负责事实问题，不扩展成全文文风重写。 |
| 表格转文字清理 | 仅在原有业务设置确实要求转换时，用适合语义的段落或列表表达。 | 不因为“少用列表”删除表格；原有信息、数字、条件和关系不可丢失。 |
| JSON修复 | 仅对实际需要重新生成的正文内容应用表达约束。 | 不修改 `anchor`、`target_text`、ID、JSON结构或已有合法正文来追求文风。 |
| 技术方案中的Agent分支 | 真实会生成或改写正文的分支使用同一政策。 | 原文归属映射、图片计划等非正文任务不能注入“直接返回正文”的要求。 |

不得只修主生成、不检查扩写；也不得把“输出正文”规则注入所有AI任务，导致原本应返回JSON的任务报错。

### R08. 写作质量诊断：增加覆盖，不增加审批

复用现有质量审计结构，至少覆盖：

1. 同一小节内的长段重复，以及不同小节中非开头位置的段落重复。
2. 标点、空白或少量衔接词变化后的近似重复候选。
3. 重复项目介绍候选和连续同主语碎片句的诊断信号。

**诊断不是最终文意裁决。** 相似度只能用于定位候选，不代表内容冗余已获证实；尤其不得把数值、否定词或主体差异抹掉后自动删文。

本版默认采用本地规则，不新增全文章节逐一AI复审。结果复用已有审计数据或开发者日志，不新增用户必须处理的待办、弹窗或导出阻断。

现有 `editorial.duplicates` 的消费者必须兼容；扩展字段采用可选字段，保留原有关键字段。文风告警不得改变 `can_proceed`、人工编制状态或任务执行成功的既有含义。

不新增“诊断后无条件自动重写全文”流程。去重首先在编排和生成源头实现；诊断负责暴露漏网问题、支持开发验收和用户主动重生成，不根据阈值静默改写已有正文。

### R09. 固定材料与人工内容保护

继续调用并验证既有人工编制保护。人工节点不进入AI写作、自动扩写或本轮自动处理。

对当前系统可识别的固定表格、承诺函、引用原文和受保护块，保留原文、结构及必要占位，只有既有允许填空的区域可填写。缺乏可靠保护标记时，不能仅凭文本相似度改写，尤其不能对整个文档执行统一润色。

普通正文中可以优化的重复表达，与招标规定必须一致的文字必须分开。不得因为“去AI味”修改明确要求原样保留的措辞。

### R10. 用户操作与审核方式保持简洁

正常用户流程不变：生成正文 → 浏览或主动编辑 → 导出 → 用户在导出文件中自行审核。

一般方法不触发确认；文风诊断不新增确认；升级至新策略不触发方法审批。不得新建 `method_pending_review` 等审批语义状态，或将一般方法写成满篇“待确认”。

人工审核不在程序内强制留痕。系统只记录自身可观察的生成、重生成、修改和导出动作，不伪造“用户已审核”的记录。

## 6. 功能流程

```text
读取现有项目、目录、已确认事实和原方案
        ↓
按现有机制识别人工节点与受保护内容
        ↓
形成章节职责与本节写作计划
（事实用于约束；内部清单不直接变成正文清单）
        ↓
构建受限长度的背景、章节边界及必要上下文
        ↓
按统一政策生成正文
（一般方法可直接补充，不等待确认）
        ↓
按原有配置执行扩写、覆盖修补、一致性修复等阶段
（只在相关正文片段上保持同一表达标准）
        ↓
本地写作质量诊断与现有任务记录
（不新增全文AI润色，不新增审批，不新增导出阻断）
        ↓
保存在现有权威正文位置，继续使用原预览和Word导出
        ↓
用户在导出后的文件中自行审阅、修改和确认
```

沿用现有阶段先后关系；本图不授权重排图片生成、扩写、审计或落盘时序。Codex 需按真实调用关系接入。

## 7. 技术实施设计

### 7.1 最小改动原则

建议新增一个 Main 侧共享政策模块，例如：

`client/electron/services/contentWritingPolicy.cjs`

该路径为**拟新增**，不是声称仓库已有。模块只提供可复用规则片段和轻量上下文格式化，不请求模型、不访问业务Store、不创建新队列。

将规则按职责拆开：事实与承诺边界、正文表达、一般方法权限、编排说明。不同任务只选择适用片段；输出协议留在各任务原有构造器中。

不要复制五份相似提示词分别维护，不将Main运行逻辑搬回Renderer，也不为本版创建通用“多Agent写作平台”。

### 7.2 现有章节合同优先复用

现有合同已能表达大多数需求，首选调整字段语义、格式化和上下文，不为文风新增大量模型必填字段。

| 既有字段 | 本版语义 |
| --- | --- |
| `section_role` | 本节需要解决的问题，而不是一段项目介绍。 |
| `must_answer_questions` | 本节必须让读者理解的回答，不要求每个问题对应一个列表项。 |
| `implementation_steps` | 方法素材与必要顺序，最终可组织为自然段或步骤。 |
| `quantitative_details` | 有依据且适用的量化要求；无依据不补数，不为凑字段加占位。 |
| `deliverables` / `acceptance_criteria` | 适用时用于解释交接和完成条件，不强制每个措施都形成独立台账。 |
| `evidence_requirements` | 保留真实证明需求，不能为了通过检查虚构证明或资格。 |
| `cross_section_boundaries` | 当前负责、其他章节负责、相关节点关系应实际传入生成上下文。 |
| `forbidden_repetition` | 明确哪些内容不应在本节再次展开；不屏蔽必要重复响应。 |
| `facts.titles` | 选择需要约束本节的事实，不代表这些变量组都应完整抄入正文。 |

格式化时只展示有意义的内容；不把大量“无”“待确认”和内部字段名诱导成输出小标题。JSON结构与ID约束保留，数组允许按既有语义为空。

若实际实现确需新增字段，采用向后兼容的可选字段，并同步规范化、校验、存储、类型和测试；不得靠模型臆造未提供的来源ID。

### 7.3 轻量章节上下文与并发兼容

保留现有文本生成并发、队列和暂停续跑机制，不为降低重复把整本标书强制改成逐节串行。

本版至少保证每节获取：当前标题路径与职责、同级章节标题与职责、本节需避免展开的背景主题、相关事实及本节写作计划。

已有成功正文可以提供少量相关段落或结尾摘录，用于避免复述和自然衔接；没有成功正文时依赖静态职责边界，不等待其他章节、不编造“前文结论”。摘录是防重复参考，不是照抄底稿。

上下文构建要求：

- 每次任务使用已落盘的完整正文快照，不读取流式半成品。
- 只选语义相关或相邻章节，配置整体预算，不将全文复制进每个请求。
- 优先保留当前章节的必要事实和要求；预算不足时先缩减辅助摘录。
- 静态职责关系按节点ID稳定组织，不能由“哪个并发任务先完成”决定某项必答内容归谁。
- 本次可见摘录和内容版本记入本地诊断元数据，便于解释并发下的差异。

不必新增AI摘要请求；可以复用已有计划、章节描述和截取的完整文本块。语义相关度选择不得为了本版新接外部向量数据库。

### 7.4 质量诊断的最低实现

保留原有重复检查的兼容返回，同时增加段落级索引，避免对所有小节全文进行不受控两两比较。

建议流程：先排除受保护块和结构标记，再对普通正文按段落或完整句组建立指纹；精确重复使用哈希索引，近似重复只在候选集合中比较。

诊断规范化可以处理空白和无语义的Markdown表现符号，但不得删除数字、单位、否定词、主体名称等含义信息。原始证据必须保留，不能只存规范化文本。

默认可从不少于40个可见字符的段落或相邻句组开始检索，阈值作为内部常量由样本测试校准。这里的长度仅是诊断候选过滤，不是句长、段长写作要求。短术语、单个名称和表格表头不能独立触发重复正文结论。

建议每个问题包含类型、节点ID、原文范围或可定位片段、命中原因、候选置信说明与是否属于保护例外。报告表达为“待核对的重复候选”，不是“已确认违规”。

### 7.5 修复协议与失败行为

局部扩写继续使用已有 `insert/replace` 和精确原文锚点，不新增无约束的整节重写操作。原有唯一匹配、范围不重叠、受保护块校验必须保留。

JSON修复只修结构和必要字段；不能为了让语言更自然去改 `target_text` 或替换目标标点。无法唯一定位时不落盘，不降级为模糊全局替换。

本地文风诊断失败应记录诊断错误，保留合法正文，不能将正文生成误标为失败。模型请求、事实冲突、补丁非法等原有问题仍按原有业务机制处理，不与文风告警混为一谈。

### 7.6 本轮不扩大的模块

不修改管理端版本，不修改Worker、R2、发布授权和下载协议；不重命名preload桥接对象；不修改模型并发数、温度或供应商配置来掩盖提示词问题。

仓库说明中存在历史命名时，以当前真实调用与类型定义核对，不在本版顺便清理全部旧名称。[S09][S10]

## 8. 策略版本、缓存与历史数据

### 8.1 策略版本

建议设置独立写作策略标识 `writing-v1.7.3`，供计划指纹、日志和测试使用。它不是客户端版本号的另一套显示来源。

更新正文编排的提示词版本，使旧计划不被当作新策略已生成的计划复用。若保持现有合同结构，可保留存储结构版本5，仅更新提示词/写作策略版本，例如 `content-plan-v5-writing-1.7.3`。具体命名按本地实际版本调整。

**不能仅为了改文风就盲目把结构版本从5改成6。** 现有规范化会拒绝不同结构版本，这可能连带丢失 `original_material` 的读取路径。[S04][S05]

### 8.2 缓存分类与处理

| 数据 | 处理 |
| --- | --- |
| 已生成的完整正文 | 保留，可继续查看和导出；不因升级自动重写。 |
| 人工编辑正文 | 保留，不能被后台风格升级覆盖。 |
| 旧策略的可重新推导计划 | 新生成或重生成时标为不新鲜，按新政策重新编排。 |
| 原方案来源映射、还原正文与来源哈希 | 作为既有内容依据保留，不因计划提示词过期一并清空。 |
| 暂停任务中已成功的小节 | 保留完成状态，不为统一风格重新跑完全部章节。 |
| 暂停任务中尚未生成的小节 | 续跑时使用新策略，记录实际策略版本，不复用缓存中的旧强制短句提示词。 |
| 旧文风诊断报告 | 不作为当前结果复用，允许重新计算。 |

结构可读取与计划可复用应分开判断。旧计划过期，不等于原文无效、需要重新导入或重新还原。

通过现有Store保存业务权威数据，不新建平行JSON权威缓存，不进行与本轮无关的大规模数据库迁移。

### 8.3 局部修改的并发保护

在既有任务锁和保存机制下核对被修改正文的版本。模型请求期间正文被用户修改时，不能直接覆盖新内容；沿用已有保护或补充最小的版本/内容哈希检查。

只在完整模型结果、阶段结束或原有规定的保存节点落盘，不按token反复存储。生成结果、状态与必要映射保持一致，不能出现页面显示新正文、导出仍使用旧副本的情况。

## 9. 操作留痕与信息保护

复用现有日志、任务状态和Token统计，至少能够定位：任务阶段、工作流类型、节点ID、写作政策版本、模型配置标识、开始结束时间、输入输出字数、计划是否重建、诊断问题数量、结果状态。

不建立逐条方法审批日志，不记录无法观察的文件外审核完成状态。

常规日志优先记录元数据和哈希。正文证据如需保留，只进入既有开发者模式本地日志，并遵守项目脱敏机制；不得把招标原文、提示词、正文、文件路径、API密钥或企业敏感资料上传到遥测服务。[S09]

生成正文不得引入无关竞争对手、其他项目单位或未经提供的客户信息。复用项目已有词语约束，不新增笼统的“AI味词库”或敏感词管理页面；真实招标主体和规定原文不能因名单匹配被自动抹除。

## 10. 验收标准

### 10.1 功能与保护条件：必须全部通过

| 编号 | 验收条件 |
| --- | --- |
| AC01 | 实际组装的正文写作请求中，不再存在强制30字拆句、固定主语及机械词汇替换的有效指令。 |
| AC02 | 首次生成、重新生成、已有方案优化、扩写及相关修订路径均接入适用的统一政策；JSON任务协议不变。 |
| AC03 | 一般实施方法自动进入正文，不弹确认、不暂停、不新增导出门槛，不带“AI建议／待用户确认”等一般方法标签。 |
| AC04 | 缺少具体人员、设备、资质、时限、质保等资料时，不自动填造；有依据的原指标准确保留。 |
| AC05 | 项目背景被明确标为理解上下文，不作为每节必写清单；本节必答事项不因去重丢失。 |
| AC06 | 人工节点、固定承诺原文、指定表格、图片引用和既有有效内容按各自保护规则保留。 |
| AC07 | 能检测固定样本中的非开头重复和轻微措辞变化的重复候选；必要重复不被自动删除。 |
| AC08 | 文风诊断不修改既有业务准入状态，不新增全篇自动AI重写。 |
| AC09 | 旧计划策略过期不造成正文、原方案映射或人工编辑丢失；升级后新写入使用新政策。 |
| AC10 | 原有并发、暂停、恢复、局部替换和Word导出链路通过回归验证。 |
| AC11 | 客户端版本来源按现有机制指向1.7.3，登录页与关于页不单独硬编码；管理端版本不被强制同步。 |
| AC12 | 实施记录区分代码测试、模型效果测试和未执行项，不虚报通过。 |

### 10.2 正文效果：采用样本对照，不用机械字数代替人工判断

| 维度 | 达标表现 | 不达标表现 |
| --- | --- | --- |
| 连贯性 | 读者能理解动作的先后、条件或因果；段落完整。 | 仍大量呈现彼此孤立的动作短句。 |
| 方法清晰度 | 可以指出具体处理对象、关键做法和必要的复核或交接。 | 主要依赖“加强、完善、确保”等口号，读完仍不知道怎么做。 |
| 重点可见性 | 需要定位的做法适度分层；表格与步骤用于合适内容。 | 清单铺满全文，或所有信息挤在巨大段落中。 |
| 章节分工 | 关键背景在合适位置交代，其他小节推进自己的内容。 | 相同主体介绍反复占据多个小节，换词后仍在重复。 |
| 事实边界 | 新方法不冒充既有事实，不增加无依据的具体承诺。 | 为了具体、量化或显得专业而补造数据与能力。 |
| 内容完整 | 必答要求、原有效方法和必要表格被保留。 | 为了简短或去重删掉响应内容，或改坏固定文字。 |

固定回归样本中，不必要的完整项目介绍不得在多个无关小节中重复；必要重复作为显式例外单独核对。不得将该样本验收表述为“任意标书绝不会重复”的保证。

| T09 | 已有明确质保期限、技术参数和真实岗位安排。 | 生成/扩写规则要求保持原值，局部处理不改数值与单位。 |
| T10 | 文中一段先说“采用”，另一段是已有证据的“已建立”。 | 不执行全局时态替换，不把计划与事实混为一谈。 |
| T11 | 两节开头不同，中间有相同长段。 | 诊断能定位中部重复及原文证据。 |
| T12 | 重复段仅更换少量衔接词或空白。 | 在固定测试样本中产生近似重复候选，保留原始差异，不自动删文。 |
| T13 | 同一短机构名称、常用术语多次出现。 | 不仅凭单个名称或术语判定正文重复。 |
| T14 | 两个相似条款仅否定词、数值、单位不同。 | 诊断保留差异；不得归一化后自动合并，不干扰事实冲突处理。 |
| T15 | 招标明确要求在两张表中重复相同承诺。 | 重复内容保留，作为保护例外，不影响导出。 |
| T16 | 人工编制节点含旧式短句。 | 所有自动写入路径均拒绝修改；不能以文风优化绕过保护。 |
| T17 | 固定承诺函、指定表格、图片与正文混合。 | 文字策略优化不改保护块、图片地址和表格结构。 |
| T18 | 已有方案含参数、承诺、列表和表格。 | 还原优化保留实质信息和来源映射，不从零替换整套方案。 |
| T19 | 局部扩写返回合法 `insert/replace`。 | 只写入对应正文块；生成片段遵循新政策，锚点保持逐字匹配。 |
| T20 | 锚点重复、目标有差异、补丁范围重叠。 | 拒绝非法写入，不退化为模糊替换或整节重写。 |
| T21 | JSON修复和原文归属映射任务。 | 返回原协议结构，不因共用文风规则改为纯正文。 |
| T22 | 一致性审计发现一处事实冲突。 | 只修冲突范围，不顺带全文润色，原审计职责不扩张。 |
| T23 | 表格需求分别为“不要／少量／适中／大量”。 | 沿用原规则；不因本版强调自然段而全部删表或转表。 |
| T24 | 两个相关章节并发生成，完成顺序相反。 | 静态职责归属稳定，不依赖谁先完成；未完成章节不被当作已写结论。 |
| T25 | 大量章节、长全文和上下文不足。 | 辅助上下文按预算截取，必需事实不被无声挤掉；不逐节重复传整本正文。 |
| T26 | 旧提示词版本计划仍具备合法结构。 | 识别为需重建的计划，但保留正文、原方案还原信息和来源映射。 |
| T27 | 任务暂停后升级，再继续未完成章节。 | 已成功正文不自动重写；未完成章节采用新政策并记录版本。 |
| T28 | 模型请求期间用户修改目标正文。 | 不静默覆盖新正文；版本或原文校验生效。 |
| T29 | 诊断模块异常或出现风格告警。 | 合法正文保留；风格问题不新增导出阻断或模型重试循环。 |
| T30 | 生成、重生成、导出与开发者日志。 | 操作有迹可查，不上传正文和密钥，不伪造文件外审核完成状态。 |
| T31 | 历史项目打开并直接导出。 | 不强制迁移文风，不自动全篇重写，仍用权威正文导出。 |
| T32 | 新版本打包与两处版本展示。 | 按既有版本来源一致显示1.7.3；管理端和发布协议无无关变更。 |

“方法是否合理”“文风是否自然”等语义效果不能仅凭请求文本断言通过，还必须执行下面的真实模型对照。

### 11.2 真实模型效果对照

至少准备六类匿名样本：服务启动、文稿与版面设计、制作及交付、质量控制、异常处理、已有方案扩写。覆盖普通段落、步骤、表格及跨章节重复场景。

每组使用相同输入、目录、事实、模型和参数，保留旧规则基线与新规则输出；重点重复场景对新版本至少再复测一次。无法取得旧版本运行结果时，可以使用可确认来源的旧输出，但必须注明对照限制。

记录阶段、模型标识、策略版本、调用次数、Token、耗时、输出差异及人工评价。经授权、确认测试环境和可用额度后执行真实模型请求，不为测试擅自新增付费供应商。

至少核对第10.2节六个维度。不能只给“更像人写的”一句主观结论；应引用具体段落说明改善和剩余问题。没有真实模型权限时，交付中明确写“模型文风验收未执行”，不得以单元测试通过代替。

样本标书如未提供，可先用自建匿名样本验证通用行为；不能声称已经复现用户原文件的问题或验证所有招标格式。

## 12. 文风标杆与反例

以下是本轮认可方向的示范，不是所有章节的固定模板。示例流程是拟议的一般方法，不代表已经核实的企业现状。

### 12.1 正例：宣传品设计与制作交接

宣传内容以确认后的文稿和图稿为依据，设计过程中同步处理文字准确性、信息层级和载体适配，避免只调整视觉效果而忽略内容表达。

**文稿核对。** 接收宣传资料后，按项目名称、单位名称、主题文案、数字及计量单位逐项核对。对前后表述不一致、信息缺失或含义不明确的内容，集中提出确认，不凭经验补写；核对后的文稿作为版面设计依据。

**版面设计。** 在文稿明确的基础上，按主标题、核心信息和辅助说明组织信息层级。门牌、桌牌突出名称与岗位识别，职责牌、制度牌兼顾内容完整和阅读顺序，展架突出展示重点，宣传册保持连续阅读逻辑。针对不同尺寸和使用距离，分别调整字号、留白和图文比例，不直接将同一版面等比例缩放套用。

**校样确认与制作交接。** 版面完成后，将校样与确认文稿逐项对照，检查文字有无遗漏、图文对应是否准确、标识使用是否一致。修改意见集中落实后提交确认，再将确认版与制作文件核对，保留相应版本和修改记录，防止旧稿误用或修改遗漏。

示例中的“提交确认”是拟议服务流程中的文稿/校样确认，不是让软件用户在正文生成过程中审批AI方法。实现时必须区分两种确认。

### 12.2 反例A：机械短句

> 我们核对文字。我们核对数字。我们统一字体。我们统一色彩。我们完成设计。我们保证质量。

缺陷是缺少处理方式和动作关系，不是这些句子短就天然错误。不能只把句号换成逗号就算修复。

### 12.3 反例B：空泛长句

> 我方将以高度负责的工作态度全面加强各项工作，通过完善机制、强化管理和深入协同，确保项目高质量实施。

句子变长，但没有增加具体做法，不符合本轮目标。

### 12.4 反例C：无依据量化

> 我方安排三名专职校对人员，所有修改均在两小时内完成，并提供无限次免费修改。

输入没有这些依据时，不得生成。不能以“让方法具体”为理由增加人员、时限和服务范围承诺。

### 12.5 反例D：换词重复背景

> 本项目由某单位采购，某单位签约，某单位负责项目管理，我方负责服务。
>
> 作为本项目的服务供应商，我方围绕上述采购、签约和管理关系开展服务。

在多个无关小节用不同词语重复相同关系，仍然是内容重复。重点应回到各节任务，而不是变换称谓躲过查重。

## 13. 共用提示词的内容基线

以下是供开发者落实的规则文本，不是交给用户手工填写的设置项。应由各构造器按任务职责组合，不将整段无差别注入JSON映射或其他非正文任务。

### 13.1 正文表达规则

> 你负责为当前投标文件章节编写或修订正文。围绕本节职责和必须回答的问题组织内容，使评审人员能够理解方案及其关键做法。
>
> 用自然、正式、清楚的中文表达。句长由语义决定，不按固定字数拆句，不要求每句以“我们”或“我方”开头。需要说明条件、因果、顺序或目的时，可以使用正常的连接表达；避免反复套用相同句式和空泛的承接语。
>
> 解释和论述优先形成完整自然段。真实步骤、并列检查项和对照信息可采用列表或表格，但不要把普通方案正文写成连续的动作清单。需要突出方法时可使用简短加粗引导语，不要求每节套用同一结构。
>
> 实施方法说明关键动作、处理方式及必要的复核或交接。根据本节需要选择展开，不机械补齐人员、时限、参数、记录和验收全部要素。不用形容词、重复表态或重新介绍项目来凑篇幅。
>
> 项目背景和全局事实用于帮助理解并约束准确性，不是要求逐节复述的内容清单。仅在本节需要时提及；其他章节负责的事项不重复完整展开，但必须保留招标要求独立响应的内容。

### 13.2 方法与事实边界

> 招标文件未详细规定的一般实施方法，可以在当前采购范围和已知条件下合理补充，并直接融入正文，不要求软件用户逐项确认，不使用“AI建议”或一般方法“待确认”标签。
>
> 不得虚构企业已有人员、设备、资质、业绩或其他事实；不得擅自增加具体数量、时限、质保、服务等级和免费服务范围等承诺。拟采用的方法不写成已经完成或已经具备的事实。
>
> 已有招标要求、项目事实和明确指标必须准确保留。不适用的量化或证明要素不必补造。真正缺失的必填资料按原有处理方式保留，不用一般方法替代，也不把所有措施写成待补信息。
>
> 不改变固定承诺原文、受保护表格、人工编制内容及当前任务不允许修改的材料。资料之间存在冲突时遵循原有冲突处理，不凭文风要求擅自裁决。

### 13.3 编排与修订补充规则

> 内部编排字段用于检查覆盖和分工，不要求最终正文按字段顺序逐项列出。只规划本节需要且有意义的要素，不适用的字段允许为空。
>
> 扩写只补当前缺口，并与相邻原文自然衔接；保留既有实质信息，不复述整段背景。修复只在当前任务允许的范围内进行。
>
> 当前任务规定的输出格式优先保留：纯正文任务只输出正文；JSON补丁任务只返回约定结构，写作要求仅作用于可生成的正文值，不修改原文锚点、ID和其他协议字段。

系统还应保留原有事实、表格、图片、目录和协议约束；本节不授权删除这些规则。

## 14. Codex 分步实施任务

按顺序执行，每步完成后记录实际修改、验证结果和未解决项。不要一次性改写全部生成服务。

### 步骤1：只读核查与实施计划

**输入：** 本规格、根目录 `AGENTS.md`、`开发说明.md`、本地工作区及现有测试。

**动作：** 核对当前分支、Git状态、客户端版本及真实调用链；找到主生成、重新生成、原方案优化、扩写、修复、表格清理、Agent相关入口和保存位置。

**输出：** 实际文件/函数清单、调用链表、与本规格基线的差异及分阶段计划。

**关键约束：** 只读核查不拉取、不重置、不合并、不推送；不覆盖未提交改动。遵守仓库对分支操作和发布的授权要求。不得将文档中的旧占位入口当作真实运行实现。

### 步骤2：统一写作政策并移除冲突规则

**输入：** 已确认的真实正文构造器及R01—R04、第13节。

**动作：** 建立轻量共用模块，替换旧短句、固定主语和词汇强制替换；保留输出协议、事实边界和已有格式要求。

**输出：** 共用政策模块、主生成接入及消息级测试。

**关键约束：** 不只是追加一句“语言自然”；不引入新句长或段落数量硬指标；不做全文文本替换；不修改独立对话提示词库。

### 步骤3：调整章节编排与事实使用语义

**输入：** 既有章节合同、全局事实、同级职责和第7.2节。

**动作：** 修改编排提示词和格式化，明确必答、方法素材、事实约束与背景的区别；传递已有排除边界；允许不适用字段为空。

**输出：** 新计划构造与格式化、背景复述防范规则、字段兼容测试。

**关键约束：** 不丢评分点、来源ID和必答要求，不删除全局事实，不增加逐条方法审批字段。

### 步骤4：接入全部相关正文写入路径

**输入：** 步骤1调用链、第5节R07及现有补丁协议。

**动作：** 让重生成、原方案优化、扩写和相关局部修订复用适用规则；检查技术方案Agent分支；保持非正文任务协议。

**输出：** 路径覆盖表、更新后的构造器、精确补丁与受保护内容回归测试。

**关键约束：** 不把“直接返回正文”注入映射和JSON修复任务；不将一致性审计改为全文润色；不解除人工写入保护。

### 步骤5：补齐轻量章节上下文

**输入：** 当前目录、计划和已落盘正文快照。

**动作：** 在既有并发框架内提供静态章节职责、必要排除主题及预算内的相关摘录；缺少已写正文时正常退回静态职责。

**输出：** 受限上下文构建、并发顺序与预算测试。

**关键约束：** 不新增AI摘要，不串行化整本生成，不逐节传全文，不伪造前文已完成状态。

### 步骤6：增强本地写作质量诊断

**输入：** 权威正文、节点职责、保护信息和原质量审计返回结构。

**动作：** 实现段落重复、轻微改写候选和碎片化表达诊断，保留可定位证据与例外。

**输出：** 兼容的诊断结果、非开头重复/近似重复/必要重复测试及性能记录。

**关键约束：** 不按相似度自动删文，不新增模型全篇复审，不改变 `can_proceed` 等既有准入语义，不新增审核界面。

### 步骤7：处理策略版本、缓存和留痕

**输入：** 现有计划指纹、Store、原方案映射、暂停续跑与日志。

**动作：** 更新提示词/策略版本；将计划过期与正文、原方案数据有效性分开；记录新生成的实际策略版本；验证用户编辑并发保护。

**输出：** 缓存兼容处理、历史项目与续跑测试、脱敏元数据日志。

**关键约束：** 不因结构版本升级清空历史正文或原方案映射；不上传正文；不创建审批状态或伪造用户审核记录。

### 步骤8：版本更新与完整验证

**输入：** 已实现代码、本地真实版本管理机制、第10—11节用例。

**动作：** 按现有机制设置客户端1.7.3并同步必要锁文件；执行单元、集成、构建、模型样本及导出回归；核对两种技术方案入口。

**输出：** 测试结果、样本对照、版本一致性检查和未执行项。

**关键约束：** 不降级本地已有版本，不改管理端版本，不擅自发布；没有模型/打包环境则如实列出限制，不虚报通过。

### 步骤9：只读审查与交付说明

**输入：** 完整diff、测试报告和本规格。

**动作：** 检查遗漏入口、规则冲突、缓存丢失、保护失效、无依据承诺及导出门槛是否被错误加入；完成针对性修复。

**输出：** 面向用户的中文变更摘要、实际修改文件清单、运行方法、验收证据、已知限制和可回退范围。

**关键约束：** “完成开发”不等于“已发布”。未经明确授权不创建远程提交、推送、合并或Release。
